刚开始接触代理工具时，会被一堆名词绕晕：Clash、Clash for Windows、Clash Verge、mihomo、机场、纯净节点、TUN 模式……它们有的是软件，有的是软件的内核，有的是卖服务的商家，根本不是一个层级的东西。

本文先把这些概念分层理清并讲透原理，再回答一个实际问题：**VS Code 远程连接的国内服务器上，怎么让 Codex 正常访问 OpenAI**。

---

## 一、一张图看懂全局关系

```text
                机场（卖节点的服务商）
                   │ 提供
                   ▼
        订阅链接（一个 URL，里面是节点列表+规则）
                   │ 导入
                   ▼
   ┌─────────────────────────────────┐
   │  GUI 客户端（壳子，负责界面）      │
   │  Clash Verge / Clash for Windows │
   │         │ RESTful API           │
   │  ┌───────────────────────────┐  │
   │  │  内核（真正干活的引擎）      │  │
   │  │  Clash / mihomo           │  │
   │  └───────────────────────────┘  │
   └─────────────────────────────────┘
                   │ 通过
                   ▼
        节点（国外服务器，负责转发流量）
                   │ 访问
                   ▼
          OpenAI / Google / GitHub ...
```

记住这个分层，后面所有名词都能对号入座：**机场卖节点 → 订阅链接把节点交给客户端 → 客户端调用内核 → 内核通过节点转发流量**。

## 二、Clash 到底是什么：一个"规则分流"的代理内核

Clash 本质上是一个**代理内核**——一个没有图形界面的单文件程序，但它不是简单的"全局 VPN"，核心能力是**按规则智能分流**。它的工作原理可以拆成三步：

**1. 入站（Inbound）**：在本机监听端口（默认 HTTP/SOCKS 混合端口 7890，TUN 模式下则是虚拟网卡），接收本机应用发来的网络请求，比如"我要连 `api.openai.com:443`"。

**2. 规则匹配（Rule）**：拿着请求的目标域名/IP，从上到下逐条匹配配置里的规则表，典型规则长这样：

```yaml
rules:
  - DOMAIN-SUFFIX,openai.com,美国节点      # openai 走美国节点
  - GEOSITE,cn,DIRECT                      # 国内网站直连
  - GEOIP,CN,DIRECT
  - MATCH,自动选择                          # 剩下的都走代理组
```

**3. 出站（Outbound）**：按匹配结果处理——`DIRECT` 直连放行；走代理则用对应协议（Shadowsocks、VMess、VLESS、Trojan、Hysteria2、TUIC 等）加密后发给境外节点，由节点替你访问目标网站，再把响应原路带回。

这里出现了两个新名词，简单交代一下：

- **代理服务器**：就是前面说的"节点"——一台位于境外的服务器，上面跑着代理服务端程序（如 Xray、sing-box）。它接收你加密发来的流量，解密后替你访问目标网站，再把响应加密送回给你。它就是你流量的"跳板"，节点、落地机说的都是它。
- **代理协议**：客户端和代理服务器之间约定的"加密通话方式"。这些协议的目的都一样——**把流量加密并伪装成正常无害的流量，让防火墙认不出、拦不下**——区别在设计年代和伪装手法：

| 协议 | 一句话特点 |
|---|---|
| Shadowsocks（SS） | 最早的轻量加密代理协议，简单高效，"机场"黑话就起源于它 |
| VMess | V2Ray 的原创协议，自带加密和身份验证 |
| VLESS | VMess 的精简版，自身不加密、配合 TLS/Reality 使用，更轻更快 |
| Trojan | 把代理流量伪装成普通 HTTPS 流量，特征少、难识别 |
| Hysteria2 / TUIC | 基于 QUIC（UDP）的新一代协议，弱网、高延迟环境下速度明显更好 |

作为用户不必深究细节：协议由机场服务端决定，mihomo 全都支持，订阅里给什么就用什么。

所以有两件事要分清：

- **Clash 不是翻墙协议**，它只是客户端/调度器。真正"翻墙"的加密协议跑在节点服务端上，Clash 只是支持连接各种协议的节点。
- **分流是 Clash 的灵魂**：国内网站直连不绕路、国外网站走节点、广告域名可拦截，互不影响。这是它相比传统全局 VPN 的最大优势。

另外，内核对外暴露一个 **RESTful API**（`external-controller`，默认 9090 端口），所有 GUI 客户端都是通过这个 API 来查询状态、切换节点、修改模式的——这就是"壳子"和"内核"能够分离的原因。

## 三、Clash 内核家族：Clash / Premium / Meta / mihomo

"Clash"这个名字背后其实是一整个家族，理清它们的谱系，看到任何衍生词都不会懵：

**1. Clash（开源内核）**：作者 Dreamacro 用 Go 编写的原版核心，2018 年前后开始流行，定义了 YAML 配置格式和规则分流这套范式，是整个生态的基石。

**2. Clash Premium（闭源内核）**：同一作者发布的闭源增强版，免费但不开源。在开源版基础上增加了当时的高级功能——**最早的 TUN 模式**、脚本扩展等。早年教程里说"想开 TUN 要换 Premium 内核"指的就是它。

**3. Clash.Meta（社区分支）**：在原版基础上由社区（MetaCubeX 组织）维护的开源分支，大幅扩展了协议支持（VLESS、Hysteria2、TUIC、WireGuard 等新协议原版都不支持），功能逐渐全面超越原版。

**4. mihomo（现役内核）**：2023 年 11 月，原版 Clash 作者清空仓库停止维护，Premium 也随之终结。社区接力棒交到了 Clash.Meta 手上，随后项目**正式改名为 mihomo**，版本号延续至今，持续活跃更新。

所以现在的结论很简单：

> **mihomo = 现役的 Clash 内核**。你看到"Clash""Meta""mihomo"混用，基本就是同一血脉在不同年代的名字。今天新装任何客户端，内核都是 mihomo。

**关键点：mihomo 是内核，不需要图形界面也能跑**——这就是后面服务器方案的答案。

## 四、Clash for Windows / Clash Verge：只是图形界面壳子

这两个都是 **GUI 客户端（壳子）**。内核本身只会默默地跑命令行，壳子负责把它包装成普通用户能用的软件：导入订阅、图形化选节点、实时流量图、一键开关系统代理。壳子通过上节说的 RESTful API 指挥内核干活，所以**同一个内核可以配任何壳子，你的订阅和节点配置在所有壳子里通用**。

- **Clash for Windows（CFW）**：曾经最流行，2023 年 11 月随原版事件由作者宣布停更并删除发布页。网上流传的都是旧版安装包，不再维护，不建议新手入坑。
- **Clash Verge（Rev）**：界面现代，内置 mihomo 内核，原版归档后由社区 Rev 版继续维护，是目前 Windows/macOS/Linux 上的主流选择。
- 其他常见壳子：macOS 上的 ClashX、移动端的 ClashMetaForAndroid / FlClash / Stash（iOS）等，同理都是"壳"。

壳子停更不可怕，换壳即可，内核和配置不受影响。

## 五、节点与机场：名字由来、节点来源、纯净节点

### "机场"为什么叫机场？

和真实机场的网络**没有任何关系**。这纯粹是圈内黑话的偶然产物：

最早的翻墙协议 Shadowsocks（SS），Logo 是一架**纸飞机**。于是网友把一台 SS 服务器戏称"一架飞机"，那批量卖 SS 账号的商家自然就成了"**机场**"——停机坪上停着很多飞机（节点），你买票（订阅）就能登机（上网）。

所以"机场"= 批量售卖节点订阅的服务商，和"小火箭（Shadowrocket）""飞机场"这些黑话同源。

### 节点到底从哪来？

节点就是一台替你转发流量的境外服务器，来源主要有两类：

**1. 自建节点**：自己买一台国外 VPS（搬瓦工、Vultr、RackNerd 等），手动部署 Xray/sing-box 等服务端。优点是 IP 独占、没人抢带宽、隐私可控；缺点是要自己运维，IP 被墙了得自己换，折腾成本高。

**2. 机场节点**：机场主批量租用 IDC 机房服务器部署好代理服务端，你付费后拿到订阅链接，里面几十上百个节点随便选。省心，但节点与陌生人共享。按网络质量，机场节点大致分三档：

- **直连节点**：你的流量直接出境到落地服务器，最便宜，晚高峰容易炸；
- **中转节点**：流量先到一个国内/边境入口服务器，再由它优化路由转发到国外落地机，晚高峰体验好不少；
- **专线节点（IPLC/IEPL）**：入口到落地之间走运营商的国际私有专线，**不过公网、不过墙**，延迟低、敏感时期也稳，最贵。

### 什么是纯净节点？

"纯净/干净"指的是**节点出口 IP 的信誉度高**，这涉及两个维度：

**维度一：IP 类型**

- **机房 IP（Datacenter）**：IP 段属于阿里云、AWS、DigitalOcean 这类数据中心。普通机场节点全是这种。
- **住宅 IP（Residential，俗称"家宽"）**：IP 段属于 Comcast、AT&T 这类家庭宽带运营商，看起来就是普通老外的家庭网络。
- **原生 IP vs 广播 IP**：原生 IP 指 IP 注册地和服务器所在地一致（美国服务器用美国注册的 IP）；广播 IP 是把别国注册的 IP 段"广播"到本地机房使用，容易被流媒体识别。

**维度二：使用历史**

一个 IP 被多少人用过、干过什么，都会被风控系统记账。普通机场节点一个 IP 几千人共享，其中总有人拿来批量注册、爬虫、发垃圾请求——这个 IP 的信誉分早就烂了。

**为什么这很重要？** OpenAI、Netflix、Google 这类服务会用 IP 信誉数据库（如 IPinfo、MaxMind）判断来访者："机房 IP + 几万人共用 + 劣迹斑斑"直接判定为代理，轻则拒绝服务（OpenAI 经典的 1020 错误、`unsupported_country_territory` 就是这么来的），重则封号。而住宅/原生、使用人数少的 IP 会被当成正常家庭用户放行。

所以：

- **纯净节点 = 原生/住宅 IP + 低共享人数 + 无劣迹历史**，价格明显更贵，适合登录 ChatGPT/Codex、注册账号、解锁流媒体等对 IP 敏感的场景；
- 日常刷网页、下代码，普通节点完全够用，不必为纯净溢价买单。

买机场时留意"原生 IP""家宽/住宅""GPT 解锁""独享 IP"等标注，说的都是这件事。

## 六、"订阅"到底是什么

很多人会困惑"我订阅了 Clash"——其实**你订阅的不是 Clash 软件，而是机场的服务**。你付费买到的是一个订阅链接，形如：

```text
https://example.com/api/v1/client/subscribe?token=xxxx
```

客户端每隔一段时间访问这个 URL，拉取一份 Clash/mihomo 格式的 YAML 配置，里面包含全部节点信息（服务器地址、端口、协议、密码）和分流规则。节点更新、增减、换 IP 都通过这个链接自动同步，所以：

- **订阅链接 = 你的账号凭证**，泄露等于账号白送别人用；
- 同一个订阅可以导入多个客户端（Windows 的 Verge、手机的 App、服务器的 mihomo），但要注意机场的**同时在线设备数限制**；
- 订阅链接一般分多种格式（Clash、Surge、V2Ray 通用订阅等），给 mihomo/Clash 系客户端用，选 **Clash 格式**。

## 七、TUN 模式：原理、那个"服务"是什么、怎么开

### 为什么需要 TUN？

Clash 默认工作在**系统代理模式**：在操作系统设置里注册一个 HTTP 代理（127.0.0.1:7890），然后**靠应用自觉遵守**。浏览器和大部分桌面软件会读这个设置，但很多命令行工具（git、curl、apt、部分语言的包管理器）、游戏、以及一些自己实现网络栈的软件根本不理会系统代理——这就是"明明开了 Clash，终端里还是连不上"的原因。

### TUN 的原理

TUN 模式换了一条更底层的路：**创建一张虚拟网卡**（TUN 是操作系统提供的三层虚拟网络设备），再修改系统路由表，把整机所有 TCP/UDP 流量都导进这张网卡。内核从网卡里读到原始 IP 包，用用户态协议栈"终结"这些连接，再按规则分流转发。

因为发生在网络层，**应用完全无感知**：不需要任何软件"配合"，不读系统代理设置的命令行工具、游戏、老软件，流量统统被接管。

| | 系统代理模式 | TUN 模式 |
|---|---|---|
| 工作层级 | 应用层（HTTP/SOCKS） | 网络层（虚拟网卡） |
| 生效原理 | 应用自觉遵守系统代理 | 系统路由强制接管 |
| 生效范围 | 浏览器等守规矩的应用 | 整机所有流量 |
| 权限要求 | 无 | 需要管理员/root |

### 安装的那个"服务"到底是什么？

以 Clash Verge Rev 为例，第一次开 TUN 时会要求安装"**服务模式**"（Service Mode）。安装的东西是一个**特权助手服务**（Clash Verge Service）：一个随系统启动、以 SYSTEM/管理员权限常驻后台的小程序，它的唯一职责就是**替没有权限的 GUI 去启动和管理内核进程**。

为什么需要它？因为"创建虚拟网卡 + 修改系统路由表"是特权操作，必须有管理员权限才能做。于是有两条路：

- **以管理员身份运行整个客户端**：右键 → 以管理员身份运行，客户端自己有权限了，也能创建 TUN 网卡。但代价是每次启动都要过 UAC 弹窗，无法静默开机自启，而且让整个图形界面程序长期持有最高权限，安全面更大。
- **安装服务模式（推荐）**：只让那个几 MB 的后台服务常驻并持有特权，GUI 和平时一样以普通用户运行。开 TUN 时 GUI 通过本地接口通知服务"帮我把内核拉起来"，服务以高权限启动 mihomo 完成建网卡、改路由。

**两种方式的效果完全一样**（都是让内核获得建网卡的权限），区别在体验和安全性上——**服务模式两方面都更好**：

- **体验**：服务模式一次安装、永久免 UAC 弹窗、支持开机自启；管理员运行每次启动都要手动授权，开机自启基本不可用。
- **安全**：管理员运行是让**整个 GUI 客户端**持有系统最高权限——而 GUI 是个"大块头"：要渲染界面、解析订阅、加载网页内容，代码量大、攻击面大，一旦存在漏洞，直接就是最高权限漏洞。服务模式遵循**最小权限原则**：持有特权的只有那个行为单一的助手服务（职责只有"拉起内核"这一件事，代码量小、行为可预期），日常打交道的 GUI 始终以普通用户权限运行，即使出问题影响也有限。

结论明确：**日常用选服务模式，它既更方便也更安全**；管理员运行只作为服务模式装不上时的临时替代。

### 如何开启

1. Clash Verge Rev → 设置页 → 先点「服务模式」旁的安装按钮（Windows 弹一次 UAC 授权，装完图标变绿）；
2. 再打开「**TUN 模式**」开关，完成。

本质就是配置文件里的 `tun.enable: true`，GUI 帮你把网卡地址、协议栈、DNS（fake-ip 防污染）等参数自动填好了。开启后建议把系统代理开关关掉，避免重复接管。

## 八、实战：国内服务器跑 mihomo，让 Codex 访问 OpenAI

### 场景与误区

场景：VS Code 通过 Remote-SSH 连到一台国内服务器，在服务器上装了官方订阅的 Codex CLI，但服务器网络访问不了 OpenAI。先厘清两个误区：

- **VS Code 连服务器本身不需要代理**——SSH 走国内网络直达服务器。需要代理的是服务器上 codex 进程发往 `api.openai.com` 的请求。
- **你订阅的不是 Clash，是机场的订阅链接**（见第六节）。服务器没有图形界面，装不了 Verge，但可以直接跑内核——**这正是 mihomo 的正确用法：它就是为无 GUI 环境设计的命令行程序**。

### 工作原理

方案的数据流如下，其实就是把第二节的"内核"从 Windows 搬到服务器上：

```text
codex / git / pip 等命令行工具
        │  http_proxy=http://127.0.0.1:7890
        ▼
服务器上的 mihomo（监听 127.0.0.1:7890）
        │  规则匹配：api.openai.com → 走代理组
        ▼
机场节点（境外服务器，加密转发）
        ▼
api.openai.com
```

因为没有 GUI，应用不会"自觉"找上门，所以要靠 `http_proxy`/`https_proxy` 环境变量**显式告诉**命令行工具"代理在 127.0.0.1:7890"。绝大多数命令行工具（curl、git、wget、pip、npm、codex）都认这两个变量。

而 mihomo 的配置文件**不用手写**：机场订阅链接返回的就是完整的 Clash/mihomo YAML（节点 + 代理组 + 规则），下载下来直接就是 mihomo 的 `config.yaml`。

### 部署步骤

```bash
# 1. 下载 mihomo（Linux x86_64；文件名中的版本号以 GitHub release 页为准）
wget https://github.com/MetaCubeX/mihomo/releases/latest/download/mihomo-linux-amd64-v1.x.x.gz
gunzip mihomo-linux-amd64-v1.x.x.gz
chmod +x mihomo-linux-amd64-v1.x.x
mv mihomo-linux-amd64-v1.x.x ~/mihomo

# 2. 拉取订阅作为配置（机场后台复制「Clash 订阅」链接）
mkdir -p ~/.config/mihomo
curl -L -o ~/.config/mihomo/config.yaml '你的订阅链接'

# 3. 启动（-d 指定配置目录）
~/mihomo -d ~/.config/mihomo
```

启动成功后，另开一个终端验证：

```bash
export https_proxy=http://127.0.0.1:7890
export http_proxy=http://127.0.0.1:7890
curl https://api.openai.com/v1/models   # 有响应（哪怕是 401）就说明代理通了
```

把两行 `export` 写进 `~/.bashrc` 永久生效，之后 codex、git、pip 全部自动走代理。

**让 mihomo 常驻后台**：简单点用 `nohup ~/mihomo -d ~/.config/mihomo &` 或 tmux；有 systemd 的话写个用户级服务更稳：

```ini
# ~/.config/systemd/user/mihomo.service
[Unit]
Description=mihomo proxy
After=network-online.target

[Service]
ExecStart=%h/mihomo -d %h/.config/mihomo
Restart=on-failure

[Install]
WantedBy=default.target
```

```bash
systemctl --user enable --now mihomo
```

**订阅更新**：节点过期或更换后，重新执行第 2 步的 `curl` 再重启 mihomo 即可；也可以写个 cron 定时任务自动更新，或改用 mihomo 的 `proxy-providers` 功能让它自己定期拉取。

**想图形化选节点**（可选）：mihomo 自带 RESTful API（`external-controller: 127.0.0.1:9090`），配置里加一行 `external-ui` 指向一个 Web 面板（如 metacubexd），就能在浏览器里切节点、看连接。

### 注意事项

- **节点要选对**：OpenAI 风控严格，订阅自带的"自动选择"组可能把你切到被标记的共享节点，导致 1020 拒绝访问。建议在配置里把 OpenAI 相关规则固定到一个纯净/原生 IP 节点（见第五节）。
- **codex 的登录流程**：登录流量横跨本地和服务器两侧，两侧走的代理不一样，详见下一节。
- **权限**：普通用户运行 mihomo 监听 7890 这种高位端口**不需要 root**；只有想在服务器上开 TUN 才需要 root 和 `/dev/net/tun` 设备（Docker/LXC 容器里通常没有）。
- **安全**：默认只监听 127.0.0.1，**其他机器**访问不到这个代理（但本机的其他用户可以，见下节）。不要为了"方便"随手开 `allow-lan: true`，那会把代理暴露给整个局域网。

### codex 登录时的流量走哪条代理？

`codex login` 的授权流程会同时在**本地电脑**和**服务器**两侧产生网络请求，两侧用的代理不一样，拆成三段看就清楚了：

```text
① 浏览器打开授权页：
   本地浏览器 ──► auth.openai.com
                 → 走【本地】网络（国内需本地 Clash）

② 授权成功后浏览器回调：
   本地浏览器 ──► localhost:1455 ──► VS Code 自动端口转发 ──► 服务器上的 codex
                 → 走 SSH 隧道，【不需要代理】

③ 换取 token，以及之后所有 API 调用：
   服务器 codex ──► mihomo(127.0.0.1:7890) ──► 节点 ──► auth/api.openai.com
                 → 走【服务器】上的 mihomo
```

逐条解释：

- **① 授权页在本地打开**：`codex login` 会打印一个授权链接，你在本地浏览器里打开并登录 ChatGPT 账号。这个请求是从本地电脑发出的，所以只要本地能正常访问 OpenAI（本地 Clash 开着）就行，和服务器无关。
- **② 回调不需要任何代理**：授权成功后，浏览器跳转到 `http://localhost:1455/auth/callback?code=...`。这里的 localhost 指本地电脑，而 codex 的回调服务监听在服务器上——VS Code Remote 检测到端口后会**自动做端口转发**，把本地的 1455 映射到服务器，浏览器一跳转，授权码就顺着已有的 SSH 隧道送达 codex，全程无需代理。如果你用的是普通 SSH 终端而不是 VS Code，手动加一条本地转发即可：`ssh -L 1455:localhost:1455 服务器`（端口号以登录时终端的实际提示为准）。
- **③ 换 token 和 API 调用必须走服务器代理**：这是最容易漏掉的一步。拿到授权码后，是**服务器上的 codex 进程**向 `auth.openai.com` 发请求换取 token，之后每一次对话请求也全部从服务器发出。这些请求通不通，取决于服务器上的 mihomo 和 `https_proxy` 环境变量——所以**务必在已经配置好代理环境的终端里执行 `codex login`**（`export` 写进 `~/.bashrc` 后重开终端即可）。否则会出现"浏览器里明明授权成功了，终端却一直卡在等待或超时"的现象——卡的就是这一步。

一句话总结：**服务器配好 mihomo + `~/.bashrc` 里 export 代理 = 登录和使用全部搞定**；登录时的浏览器环节由 VS Code 自动转发回本地完成，本地浏览器该开代理开代理，不需要你额外做任何远程端口转发。

### 其他用户能蹭我的代理吗？

**能，这是共享服务器上必须意识到的问题。** `127.0.0.1` 是整台机器共享的本机回环地址，并不专属于你的账号——只要 mihomo 在监听 7890 端口，**同一台服务器上的任何用户**都能在自己的终端里 `export https_proxy=http://127.0.0.1:7890` 蹭你的代理：烧的是你的机场流量，访问记录也算在你的订阅头上。

如果服务器是你一个人独占的，无所谓；如果是多人共享的服务器，建议做以下防护：

**1. 给代理加账号密码**（最有效）。在 `config.yaml` 里加认证配置，mihomo 的 HTTP/SOCKS 入站就会要求登录：

```yaml
authentication:
  - "你的用户名:你的密码"
```

使用时代理地址变成：

```bash
export https_proxy=http://你的用户名:你的密码@127.0.0.1:7890
export http_proxy=http://你的用户名:你的密码@127.0.0.1:7890
```

**2. 换一个不常见的端口**。把默认的 7890 改成五位随机端口，能挡住顺手扫描和照抄默认配置的人，但挡不住刻意探测，只能当辅助手段。

**3. 锁好配置文件权限**。`config.yaml` 里有全部节点的地址、密码和订阅信息，务必收紧权限：

```bash
chmod 600 ~/.config/mihomo/config.yaml
```

否则其他用户直接读文件就能拿到节点——那样连你的代理都不用借，自己配一个客户端就用了。

**4.（有 root 时）用防火墙按用户放行**。`iptables` 的 `-m owner` 模块可以只允许你的 UID 访问该端口，最彻底，但共享服务器上你一般没有 root。

日常组合：**加认证 + chmod 600** 基本就够了。

### 方案 B：复用本机 Clash，不动服务器

如果不想在服务器上装任何东西，也可以通过 SSH 反向隧道把本机 Windows 的 Clash 代理"借"给服务器用，VS Code、FinalShell、命令行工具都能稳定复用。这套方案我单独写过一篇完整指南：[《让远程 Linux 服务器稳定复用本机 Clash：SSH 反向代理完整指南》]({% post_url 2026-07-29-remote-server-via-local-proxy-complete-guide %})。

两个方案怎么选：**服务器长期需要代理、多人共用、或本机不常开机 → 方案 A（服务器跑 mihomo）；只是临时用用、不想动服务器 → 方案 B（反向隧道借本机的）**。
