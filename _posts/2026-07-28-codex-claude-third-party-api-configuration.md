> 本文记录我在实际开发中，为 Codex、Claude、VS Code 插件、桌面端应用和 CLI 配置官方账号或第三方 API 的方法。重点介绍如何使用 CC Switch 间接修改配置文件，以及如何把本地配置迁移到 VS Code Remote SSH 连接的远程服务器。
>
> 本文中的配置字段和文件结构可能随客户端版本变化。修改之前请先备份原文件，并以当前客户端、API 服务商和 CC Switch 所生成的配置为准。

## 一、这篇文章要解决什么问题？

在日常开发中，我们可能会同时使用多种 AI 编程工具：

- VS Code 中的 Codex 插件；
- VS Code 中的 Claude 插件；
- Codex 桌面端应用；
- Claude 桌面端应用；
- Codex CLI；
- Claude Code CLI；
- VS Code Remote SSH 远程开发环境中的 Codex、Claude 插件。

这些客户端最终都需要知道三类信息：

1. **使用哪个模型或服务商**；
2. **向哪个 API 地址发送请求**；
3. **使用哪个 API Key 或登录凭据完成认证**。

如果每个客户端都单独配置，不仅麻烦，还很容易出现配置不一致。CC Switch 的价值就在于：它可以帮我们管理多个服务商配置，并间接生成或修改 Codex、Claude 所使用的配置文件。

本文主要介绍三种场景：

1. 在本地通过 CC Switch 配置第三方 API；
2. 把本地配置迁移到 VS Code 远程服务器；
3. 使用自己的官方账号时，让无法直连服务的远程服务器通过本地代理联网。

## 二、开始之前：先理解配置到底存在哪里

虽然我们使用的是 VS Code 插件、桌面应用或 CLI，但它们通常会从当前操作系统用户的主目录中读取配置。

### 2.1 什么是用户主目录？

常见位置如下：

```text
Windows: C:\Users\你的用户名\
Linux:   /home/你的用户名/
macOS:   /Users/你的用户名/
```

在终端中通常可以用下面的方式表示当前用户主目录：

```text
Windows PowerShell: $HOME
Linux/macOS:        ~
```

### 2.2 Claude 的主要配置目录

Claude Code 的用户级配置目录通常是：

```text
~/.claude/
```

主要配置文件通常是：

```text
~/.claude/settings.json
```

需要特别注意，文件名通常是 **`settings.json`**，中间有字母 `s`，不是 `setting.json`。

在 Windows 上，它可能对应：

```text
C:\Users\你的用户名\.claude\settings.json
```

在 Linux 服务器上，它通常对应：

```text
/home/你的用户名/.claude/settings.json
```

### 2.3 Codex 的主要配置目录

Codex 的用户级配置目录通常是：

```text
~/.codex/
```

本文重点关注两个文件：

```text
~/.codex/config.toml
~/.codex/auth.json
```

它们的职责可以简单理解为：

| 文件 | 主要作用 |
| --- | --- |
| `config.toml` | 模型、服务商、API 地址和客户端行为等配置 |
| `auth.json` | API Key、登录认证或其他身份凭据 |

不同版本的 Codex 可能调整字段名称和认证方式。因此，最稳妥的方法不是凭空手写完整配置，而是先让 CC Switch 或客户端生成可用配置，再在此基础上修改。

### 2.4 为什么 VS Code 插件也会读取这些文件？

VS Code 插件虽然运行在编辑器里，但插件通常仍会调用本机或远程环境中的对应服务，并读取该环境当前用户的配置目录。

因此：

- **本地 VS Code** 通常读取本地用户目录中的 `.claude` 和 `.codex`；
- **Remote SSH 模式下的 VS Code** 通常读取远程服务器用户目录中的 `.claude` 和 `.codex`；
- 本地配置好了，不代表远程环境会自动继承。

这也是远程开发时需要再次配置的根本原因。

## 三、使用 CC Switch 管理第三方 API

### 3.1 CC Switch 在这里做什么？

可以把 CC Switch 理解为一个配置切换工具。我们可以在里面维护不同的服务商，例如：

- 官方服务；
- DeepSeek 等兼容服务；
- 自建网关；
- 公司内部网关；
- 合法合规的第三方 API 中转服务。

每个服务商配置通常包括：

```text
名称 + API 地址 + API Key + 模型名称 + 协议类型
```

切换服务商时，CC Switch 可以帮助更新 Claude 或 Codex 对应的配置文件，从而避免反复手动编辑。

### 3.2 推荐的操作流程

一个比较稳妥的流程是：

1. 关闭或退出正在运行的 Codex、Claude 客户端；
2. 备份原有配置文件；
3. 在 CC Switch 中新增服务商；
4. 填写服务商提供的 API 地址、API Key 和模型名称；
5. 选择要应用到的客户端；
6. 在 CC Switch 中执行切换或写入配置；
7. 检查最终生成的配置文件；
8. 重新启动插件、桌面端或 CLI；
9. 发送一个简单请求，确认连接、认证和模型响应都正常。

之所以建议先关闭客户端，是因为部分程序会在退出时重新写入配置文件。如果一边运行一边修改，可能发生刚写入的配置又被客户端覆盖的情况。

### 3.3 修改前先备份

建议为配置文件创建备份：

```text
settings.json → settings.json.bak
config.toml   → config.toml.bak
auth.json     → auth.json.bak
```

如果切换后客户端无法启动，可以快速恢复原文件。

### 3.4 API Key 的安全原则

API Key 相当于账号密码，必须注意：

- 不要把真实 API Key 写进博客、截图或聊天记录；
- 不要提交到 Git 仓库；
- 不要上传包含真实凭据的 `auth.json` 或 `settings.json`；
- 不要使用来源不明的公共中转站；
- 优先选择可信、合规并明确说明数据处理方式的服务商；
- 如果怀疑密钥泄露，应立即在服务商后台撤销并重新生成；
- 服务器上的认证文件应只允许当前用户读取。

Linux 中可以适当收紧文件权限：

```bash
chmod 700 ~/.claude ~/.codex
chmod 600 ~/.claude/settings.json
chmod 600 ~/.codex/config.toml ~/.codex/auth.json
```

Windows 用户则应避免把这些文件放入公共共享目录，并检查目录访问权限。

## 四、配置 Claude 使用第三方 API

### 4.1 推荐优先使用 CC Switch 写入

对于 Claude，最简单的方法通常是：

1. 在 CC Switch 中添加 Claude 服务商；
2. 填写 API 地址；
3. 填写 API Key；
4. 填写或选择模型名称；
5. 应用配置；
6. 检查 `~/.claude/settings.json`。

这样可以减少 JSON 格式错误，也能避免漏掉服务商所需的额外字段。

### 4.2 settings.json 的基本结构

第三方 API 常通过环境变量告诉 Claude Code 使用哪个地址和凭据。示意配置如下：

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://你的服务地址",
    "ANTHROPIC_AUTH_TOKEN": "你的APIKey"
  }
}
```

某些服务商可能要求使用其他字段，例如：

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://你的服务地址",
    "ANTHROPIC_API_KEY": "你的APIKey"
  }
}
```

到底使用 `ANTHROPIC_AUTH_TOKEN` 还是 `ANTHROPIC_API_KEY`，应以当前客户端以及 API 服务商的说明为准。不要同时盲目填写多个冲突的认证字段。

### 4.3 不要覆盖已有配置

如果 `settings.json` 中已经存在权限、环境变量或其他设置，不要直接把整个文件替换成一个只有 API 配置的新文件。

例如原文件是：

```json
{
  "permissions": {
    "allow": [
      "Bash(git status:*)"
    ]
  }
}
```

应该合并成：

```json
{
  "env": {
    "ANTHROPIC_BASE_URL": "https://你的服务地址",
    "ANTHROPIC_AUTH_TOKEN": "你的APIKey"
  },
  "permissions": {
    "allow": [
      "Bash(git status:*)"
    ]
  }
}
```

而不是把 `permissions` 整段删掉。

### 4.4 JSON 最容易出现的错误

JSON 格式要求严格，常见错误包括：

```text
1. 最后一项后面多写了逗号；
2. 使用了单引号而不是双引号；
3. 少写或多写了大括号；
4. 同一个键重复出现；
5. 把 Windows 路径中的反斜杠当成普通字符；
6. 在 JSON 中直接写注释。
```

错误示例：

```json
{
  "env": {
    "ANTHROPIC_AUTH_TOKEN": "xxx",
  }
}
```

最后一个字段后面的逗号会导致标准 JSON 解析失败。

### 4.5 手动从 CC Switch 复制配置

如果不希望 CC Switch 自动写文件，也可以：

1. 在 CC Switch 中生成或查看目标配置；
2. 复制生成的 JSON 内容；
3. 打开 `~/.claude/settings.json`；
4. 备份现有文件；
5. 合并或替换相关配置；
6. 保存后重启 Claude Code 或插件。

需要强调的是，**合并**通常比整文件覆盖更安全，因为原文件中可能还有权限、Hook、插件或个性化设置。

### 4.6 验证 Claude 配置

配置后，可以从几个方面验证：

1. Claude Code CLI 能否正常启动；
2. 是否可以发送最简单的问答；
3. 是否出现 401、403、404 或模型不存在错误；
4. VS Code Claude 插件是否能正常创建会话；
5. CC Switch 当前选中的服务商是否与文件内容一致。

常见错误含义：

| 错误 | 常见原因 |
| --- | --- |
| 401 Unauthorized | API Key 错误、过期或认证字段不匹配 |
| 403 Forbidden | 账号没有模型权限、服务商拒绝访问 |
| 404 Not Found | API 地址或路径错误，或者模型名称不存在 |
| 429 Too Many Requests | 额度耗尽、请求过快或服务商限流 |
| Connection refused | 地址或端口错误，目标服务未启动 |
| Timeout | 网络不通、代理异常或服务响应过慢 |

## 五、配置 Codex 使用第三方 API

### 5.1 Codex 的两个关键文件

Codex 主要关注：

```text
~/.codex/config.toml
~/.codex/auth.json
```

其中：

- `config.toml` 决定模型、服务商和 API 地址等行为；
- `auth.json` 保存认证信息；
- CC Switch 可以间接维护这些文件；
- 也可以从 CC Switch 复制配置后手动写入。

### 5.2 config.toml 是什么格式？

TOML 是一种配置文件格式，常见写法如下：

```toml
model = "你的模型名称"
model_provider = "custom"

[model_providers.custom]
name = "自定义服务商"
base_url = "https://你的服务地址"
env_key = "你的密钥环境变量名"
```

这只是结构示意。具体服务商可能还要求配置协议类型、请求格式、额外请求头或其他字段。尤其要注意，服务商可能支持的是不同接口协议：

- Responses API 兼容协议；
- Chat Completions 兼容协议；
- 服务商自定义协议。

如果协议选错，可能出现地址能访问、认证也成功，但请求格式不被服务端接受的情况。因此应优先使用 CC Switch 生成的配置，并以当前 Codex 版本和服务商要求为准。

### 5.3 auth.json 的作用

`auth.json` 用于保存 Codex 的认证信息。示意结构可能类似：

```json
{
  "OPENAI_API_KEY": "你的APIKey"
}
```

不同版本、登录方式和服务商生成的结构可能不同，因此不建议照抄网上的固定模板。更可靠的做法是：

1. 先通过 CC Switch 或 Codex 完成一次配置；
2. 查看实际生成的 `auth.json`；
3. 在迁移到其他机器时复制这个已经验证可用的文件；
4. 复制后检查权限并重启客户端。

### 5.4 从 CC Switch 手动导入 Codex 配置

如果自动切换没有生效，可以手动处理：

1. 在 CC Switch 中选择目标服务商；
2. 复制 Codex 对应的 `config.toml` 内容；
3. 备份本地 `~/.codex/config.toml`；
4. 把配置合并或写入文件；
5. 复制 CC Switch 生成的认证内容；
6. 备份并更新 `~/.codex/auth.json`；
7. 重新启动 Codex CLI、VS Code 插件或桌面应用；
8. 使用一个简单任务验证。

### 5.5 关于配置中的 Windows 路径

在我的实践中，把本地 Windows 的 `config.toml` 复制到 Linux 远程服务器后，即使文件中还保留了一些 Windows 路径，Codex 仍然可以正常启动。

不过，这只能说明**当前版本和当前使用场景没有执行到这些路径相关配置**，不能保证所有功能都正常，也不能保证后续版本仍然兼容。

更稳妥的做法是：

1. 找出配置中明显的 Windows 路径；
2. 判断这些字段是否在远程环境中会用到；
3. 能改成 Linux 路径的尽量改掉；
4. 暂时不用的功能可以移除或禁用；
5. 每次升级 Codex 后重新验证。

也就是说，"直接复制后能启动"是一条有用的实践经验，但不应把它理解成"跨系统路径永远不需要处理"。

## 六、本地 VS Code、桌面端和 CLI 的配置关系

### 6.1 为什么一次配置可能多个客户端都能用？

如果多个客户端都读取相同用户目录下的配置文件，那么 CC Switch 修改一次后，它们就可能共同生效：

```text
CC Switch
   │
   ├── 修改 ~/.claude/settings.json
   │      ├── Claude Code CLI
   │      ├── VS Code Claude 插件
   │      └── 部分 Claude 桌面端集成
   │
   └── 修改 ~/.codex/config.toml 和 auth.json
          ├── Codex CLI
          ├── VS Code Codex 插件
          └── Codex 桌面端应用
```

但是，不同客户端版本可能有自己的登录缓存、进程环境变量或额外配置。修改后如果没有立即生效，优先尝试：

1. 完全退出客户端；
2. 关闭 VS Code 的相关窗口；
3. 重新打开终端；
4. 重新启动客户端；
5. 必要时退出旧账号或清理失效会话后重新认证。

### 6.2 推荐的本地验证顺序

为了方便定位问题，建议按以下顺序测试：

1. 先测试 CLI；
2. CLI 正常后再测试 VS Code 插件；
3. 最后测试桌面端应用。

CLI 的错误日志通常最直接。如果三个客户端一起测试，一旦失败，很难判断是 API 配置问题、插件问题，还是桌面端缓存问题。

## 七、VS Code Remote SSH 远程开发配置

### 7.1 最重要的概念：插件实际运行在哪里？

使用 VS Code Remote SSH 时，界面虽然显示在本地电脑上，但很多扩展的后端进程实际运行在远程服务器上。

因此，远程环境需要自己的：

- Claude/Codex 插件；
- Claude/Codex CLI 或对应运行组件；
- `.claude` 配置目录；
- `.codex` 配置目录；
- 网络连接和代理配置；
- API Key 或账号认证信息。

### 7.2 在远程侧安装插件

连接远程服务器后，在 VS Code 扩展页面中通常会看到类似：

```text
Install in SSH: 服务器名称
```

需要把 Claude 和 Codex 插件安装到**远程侧**，而不只是安装在本地。

判断方式：插件页面应明确显示它已安装在当前远程环境中。

### 7.3 找到远程服务器的用户目录

登录服务器后执行：

```bash
whoami
printf '%s\n' "$HOME"
```

假设输出的用户目录是：

```text
/home/devuser
```

那么配置目录通常是：

```text
/home/devuser/.claude
/home/devuser/.codex
```

注意不要把配置复制给了错误用户。例如，你用 `devuser` 连接，但把文件放进 `/root/.claude`，插件通常不会读取到。

### 7.4 创建配置目录

如果目录不存在，可以创建：

```bash
mkdir -p ~/.claude ~/.codex
chmod 700 ~/.claude ~/.codex
```

### 7.5 复制 Claude 配置到远程服务器

本地已经验证过的 Claude 配置，可以复制到远程服务器：

```text
本地 ~/.claude/settings.json
          ↓
远程 ~/.claude/settings.json
```

复制方式可以选择：

- VS Code 文件资源管理器；
- Remote SSH 远程窗口手动粘贴；
- `scp`；
- 安全文件传输工具。

复制后检查：

```bash
chmod 600 ~/.claude/settings.json
```

然后重新加载 VS Code 远程窗口或重启插件。

### 7.6 复制 Codex 配置到远程服务器

Codex 同理：

```text
本地 ~/.codex/config.toml
          ↓
远程 ~/.codex/config.toml

本地 ~/.codex/auth.json
          ↓
远程 ~/.codex/auth.json
```

复制后检查权限：

```bash
chmod 600 ~/.codex/config.toml ~/.codex/auth.json
```

然后在远程终端中测试 Codex CLI，再测试 VS Code 插件。

### 7.7 直接复制配置时要检查什么？

复制之前或之后建议检查以下内容：

| 检查项 | 说明 |
| --- | --- |
| API Key | 是否仍然有效，是否允许在服务器上使用 |
| API 地址 | 远程服务器是否能访问该地址 |
| 文件路径 | 是否包含仅在 Windows 存在的路径 |
| 环境变量 | 远程进程是否能读取到 |
| 文件权限 | 当前远程用户是否有读取权限 |
| 模型名称 | 服务商是否支持该模型 |
| 代理地址 | `127.0.0.1` 在远程服务器上代表服务器自身，不代表本地电脑 |
| JSON/TOML 格式 | 复制过程中是否破坏了格式 |

### 7.8 推荐的远程验证流程

配置完成后不要立即在复杂项目中测试，建议：

1. 远程终端确认当前用户和 `$HOME`；
2. 确认配置文件位于正确目录；
3. 确认文件权限；
4. 测试目标 API 地址的网络可达性；
5. 启动 Claude 或 Codex CLI；
6. 发送一个不涉及项目文件的简单问题；
7. CLI 正常后重新加载 VS Code 窗口；
8. 再测试远程插件能否读取项目和响应。

这样可以快速判断问题发生在哪一层。

## 八、官方账号场景：让远程服务器使用本地代理

### 8.1 这个场景为什么更复杂？

使用第三方 API 时，只要服务器能访问中转 API 地址，通常直接复制配置即可。

但如果使用自己的官方账号，而远程服务器无法直接访问对应服务，就需要让远程服务器的请求通过本地电脑的网络代理转发出去。

核心链路是：

```text
远程服务器上的 Codex/Claude
            │
            ▼
远程服务器上的转发端口
            │  SSH 端口转发
            ▼
本地电脑上的代理端口
            │
            ▼
目标服务
```

这里的关键不是简单地在服务器中写：

```text
HTTP_PROXY=http://127.0.0.1:7890
```

因为服务器中的 `127.0.0.1` 指向**服务器自己**，不是你的本地电脑。必须先通过 SSH 建立端口映射，让远程服务器能够访问到本地代理。

### 8.2 先确认本地代理类型和端口

本地代理程序通常提供以下一种或多种端口：

- HTTP 代理端口；
- HTTPS 代理端口；
- SOCKS5 代理端口；
- 混合端口。

假设本地代理监听：

```text
127.0.0.1:7890
```

请以你自己的代理软件实际设置为准，不要直接照抄端口。

### 8.3 使用 SSH 远程端口转发

目标是让远程服务器上的某个端口，例如 `17890`，转发到本地电脑的 `127.0.0.1:7890`。

SSH 命令示意：

```bash
ssh -R 17890:127.0.0.1:7890 远程用户名@服务器地址
```

含义是：

```text
远程服务器 127.0.0.1:17890
             ↓
本地电脑 127.0.0.1:7890
```

建立连接后，远程服务器中的程序就可以把代理设置成：

```text
http://127.0.0.1:17890
```

需要注意：

- 该 SSH 会话断开后，端口转发也会失效；
- 远程端口 `17890` 不能被其他程序占用；
- 本地代理必须正在运行；
- 本地代理需要允许来自该 SSH 转发的连接；
- 不要把代理端口无认证地暴露到公网。

### 8.4 在 SSH 配置文件中持久化

可以在本地 SSH 配置中为服务器增加远程转发。示意：

```sshconfig
Host my-dev-server
    HostName 你的服务器地址
    User 你的远程用户名
    RemoteForward 17890 127.0.0.1:7890
    ServerAliveInterval 60
    ServerAliveCountMax 3
```

之后 VS Code Remote SSH 连接 `my-dev-server` 时，可以自动建立转发。

请确认本地 OpenSSH 和远程服务器策略允许远程端口转发。如果管理员禁用了 TCP forwarding，需要联系服务器管理员按组织安全规范处理。

### 8.5 在远程服务器配置代理环境变量

端口映射建立后，可以在远程终端临时设置：

```bash
export HTTP_PROXY=http://127.0.0.1:17890
export HTTPS_PROXY=http://127.0.0.1:17890
export ALL_PROXY=http://127.0.0.1:17890
```

有些程序只识别小写变量，可以同时设置：

```bash
export http_proxy="$HTTP_PROXY"
export https_proxy="$HTTPS_PROXY"
export all_proxy="$ALL_PROXY"
```

如果本地提供的是 SOCKS5 代理，应按程序支持情况使用：

```bash
export ALL_PROXY=socks5://127.0.0.1:17890
```

不是所有客户端都支持相同的代理变量或 SOCKS5 协议。如果 CLI 正常而 VS Code 插件不正常，可能是插件进程没有继承终端环境变量。

### 8.6 为什么终端能用，VS Code 插件却不能用？

你在远程终端中执行 `export`，只对**当前终端进程及其子进程**生效。已经启动的 VS Code Remote 扩展宿主不一定会读取到。

可以考虑：

1. 在建立 Remote SSH 连接之前准备代理环境；
2. 把代理变量配置到远程登录 Shell 的环境文件中；
3. 在客户端自身支持的配置文件中设置代理；
4. 重新加载或重启 VS Code Remote Server；
5. 完全断开后重新建立 Remote SSH 连接。

如果写入 Shell 配置文件，要避免影响不需要代理的命令。可以按需设置 `NO_PROXY`：

```bash
export NO_PROXY=localhost,127.0.0.1,::1
export no_proxy="$NO_PROXY"
```

在公司或受管服务器中修改全局代理前，应遵循管理员和网络安全要求。

### 8.7 检查端口是否真的在工作

在远程服务器中可以先检查端口监听情况：

```bash
ss -lnt | grep 17890
```

也可以用当前系统已有的网络工具测试代理，但不要在命令中打印或上传真实 API Key。

如果端口不存在，优先检查：

1. VS Code/SSH 连接是否带上远程转发配置；
2. SSH 会话是否仍然在线；
3. 远程端口是否被占用；
4. SSH 服务端是否允许 TCP 转发；
5. 本地代理程序是否正在监听正确端口。

### 8.8 代理方案的安全注意事项

- 只监听远程服务器的回环地址，避免对公网开放；
- 不要使用 `0.0.0.0` 暴露无认证代理；
- 不要在多人共享服务器中暴露个人账号代理；
- 不要让不可信用户读取你的认证配置；
- 遵守服务条款、组织政策和当地法律；
- 仅将该方案用于自己拥有或获授权使用的账号和服务器。

## 九、官方账号与第三方 API 应该如何选择？

两种方式各有特点：

| 方式 | 优点 | 注意事项 |
| --- | --- | --- |
| 官方账号/官方 API | 来源明确、功能和兼容性通常最好 | 服务器网络必须可达，需处理登录或代理问题 |
| 第三方 API/中转站 | 网络接入方便，可能支持统一管理多个模型 | 要评估数据隐私、可靠性、计费和合规性 |
| 自建网关 | 控制力强，可统一审计、限流和路由 | 需要自己维护服务、安全和可用性 |

选择第三方服务时，至少确认：

1. 服务商是否合法合规；
2. 是否会存储请求内容和代码；
3. 是否支持删除日志；
4. API Key 和请求数据如何保护；
5. 计费方式是否透明；
6. 模型名称和协议是否真实兼容；
7. 是否适合发送公司的私有代码。

对于公司源码、客户数据和敏感项目，不要只看价格或速度，应优先遵守公司的安全制度。

## 十、常见故障排查

### 10.1 CC Switch 切换后没有生效

按以下顺序检查：

1. CC Switch 是否选择了正确的客户端；
2. 实际修改的是不是当前用户目录；
3. `settings.json`、`config.toml` 和 `auth.json` 的修改时间是否变化；
4. 客户端是否仍在使用旧的登录缓存；
5. 是否完全退出并重新启动；
6. 是否存在项目级配置覆盖用户级配置；
7. 环境变量是否覆盖了文件配置。

### 10.2 本地可用，远程不可用

重点检查：

```text
远程插件是否已安装？
配置是否复制到远程用户的 HOME？
远程服务器是否能访问 API？
文件权限是否正确？
远程用户是否和预期一致？
代理端口转发是否仍然存在？
```

### 10.3 CLI 可用，VS Code 插件不可用

可能原因：

- 插件安装在本地而不是远程；
- 插件进程没有继承终端环境变量；
- VS Code Remote Server 没有重启；
- 插件使用了不同的配置目录；
- 插件版本与 CLI 版本不一致；
- 插件仍然保留旧会话或旧账号状态。

### 10.4 401 或认证失败

检查：

- API Key 有没有多复制空格或换行；
- Key 是否过期、被撤销或额度不足；
- 认证字段名称是否正确；
- 服务商要求的请求头是否不同；
- `auth.json` 是否被客户端重新覆盖；
- 远程复制后文件编码是否正常。

### 10.5 模型不存在

模型的"展示名称"和 API 使用的"模型 ID"可能不同。确认：

- 模型 ID 是否完全一致；
- 账号是否有权限；
- 服务商是否要求自定义模型映射；
- Codex/Claude 客户端是否支持该协议和模型能力；
- API 地址是否指向正确版本。

### 10.6 TOML 或 JSON 解析失败

排查方法：

1. 恢复备份，确认客户端可以启动；
2. 每次只增加一小段配置；
3. 检查引号、括号、逗号和字段重复；
4. 不要把 JSON 语法直接放进 TOML；
5. 不要把 TOML 表头写进 JSON；
6. 优先重新让 CC Switch 生成一次正确配置。

### 10.7 远程代理偶尔中断

常见原因：

- 本地电脑休眠；
- 网络切换；
- SSH 会话断开；
- VS Code Remote SSH 自动重连后没有恢复转发；
- 本地代理重启后端口变化；
- 服务器空闲超时断开连接。

可以通过 SSH KeepAlive、固定本地代理端口，以及重新连接后检查远程监听端口来改善稳定性。

## 十二、最终配置思路总结

整套配置方法可以归纳为一句话：

> 先用 CC Switch 在本地生成并验证可用配置，再根据客户端实际运行的位置，把 `.claude` 和 `.codex` 中的相关文件复制或合并到对应环境；如果远程服务器不能直连目标服务，再通过安全的 SSH 端口转发让远程请求使用本地代理。

整体结构如下：

```text
                           ┌──────────────────┐
                           │    CC Switch     │
                           │ 管理服务商/APIKey │
                           └────────┬─────────┘
                                    │
                   ┌────────────────┴────────────────┐
                   │                                 │
          ┌────────▼────────┐               ┌────────▼────────┐
          │ ~/.claude/      │               │ ~/.codex/       │
          │ settings.json   │               │ config.toml     │
          │                 │               │ auth.json       │
          └────────┬────────┘               └────────┬────────┘
                   │                                 │
          Claude CLI / 插件 / 桌面端         Codex CLI / 插件 / 桌面端
                   │                                 │
                   └────────────────┬────────────────┘
                                    │
                         官方 API / 第三方 API
```

远程开发时，再增加一层：

```text
本地已验证配置
      │
      ├── 复制到远程 ~/.claude/
      ├── 复制到远程 ~/.codex/
      └── 必要时建立 SSH 代理端口转发
                    │
                    ▼
          VS Code Remote SSH 插件
```

最重要的实践原则是：

1. **先备份，再修改**；
2. **先在 CLI 验证，再测试插件和桌面端**；
3. **配置要放在程序实际运行环境的用户目录中**；
4. **API Key 不上传、不截图、不提交 Git**；
5. **本地能用不代表远程能用，远程必须单独检查网络和配置**；
6. **跨平台直接复制可能暂时可用，但仍应检查路径和环境差异**；
7. **第三方服务要重点评估隐私、稳定性和合规性**；
8. **代理只用于自己拥有或获授权使用的环境，不要对公网开放**。

按照这套思路配置后，本地 VS Code、桌面端、CLI，以及 VS Code Remote SSH 远程开发中的 Codex 和 Claude，都可以用同一套方法进行管理和排查。
