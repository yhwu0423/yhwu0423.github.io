> 本文提供一条面向 **AI 应用开发、Agent 工程和 Coding Agent** 方向的 20 周项目制学习路线。主项目不是聊天 Demo，而是一个能够理解代码库、调用受控工具、检索证据并辅助修复测试失败的 Coding Agent。
>
> 这不是“零基础学完即可获得 Offer”的承诺。路线默认读者已经具备 Python、Git、命令行、HTTP、SQL 和基础测试能力；完全初学者应先完成“开始前准备”，通常还需要额外 4～8 周。20 周默认每周投入 12～15 小时，时间不足时应延长周期，不能删掉安全、测试和评估环节。

## 一、先明确目标：用一个项目积累工程证据

### 1. 这条路线适合谁？

适合以下读者：

- 已经能够用 Python 写出小程序，想转向 LLM 应用或 Agent 工程；
- 希望把“会调用模型 API”进一步提升为“会设计、测试和部署 AI 后端”；
- 愿意连续维护一个项目，而不是每周更换一个新框架；
- 目标岗位偏向 AI 应用开发、Agent 开发、RAG 工程、LLM 应用后端或 AI 平台应用方向。

不适合作为以下路线的替代品：

- 预训练、SFT、RLHF、LoRA 和模型算法研究；
- GPU 推理、量化、vLLM 和大规模分布式 Infra；
- Kubernetes、复杂微服务、多租户平台和企业级运营系统；
- 只想通过复制教程快速做出一个网页聊天界面的学习者。

### 2. 20 周结束时，应该争取拿到什么？

“完成”不以框架数量或 GitHub 仓库数量衡量，而以能否提供可复现的工程证据衡量。理想情况下，主仓库应包含：

1. 一个不依赖 Agent 框架的模型调用与工具循环；
2. 一个有权限策略、人工审批、超时、重试和审计日志的受控工具层；
3. 一个能够暂停、恢复并避免重复副作用的状态化工作流；
4. 一个基于已有工具接口接入的 MCP Server/Client；
5. 一个能够检索代码证据、给出引用并在无证据时拒答的代码库 RAG；
6. 一组软件测试、评估任务和安全案例，以及失败分类报告；
7. 一份 Docker 启动说明、架构图、演示视频、成本/延迟记录和已知限制。

这些材料可以成为简历和面试的证据，但不等于录用结果。是否适合投递，仍取决于目标岗位的具体要求、学历和在校身份、实习时间、地区、招聘批次、算法面试和沟通表现。

### 3. 主项目的边界

主项目统一命名为 `agent-lab`，目标场景是：

> 用户提出一个代码任务，Agent 在授权工作区内搜索相关代码，形成修改计划，经过审批后生成补丁，运行固定测试，并根据测试结果决定是否需要继续修复。

第一版只处理自己拥有或明确获授权的测试仓库。代码、README、Issue 和注释中的自然语言都视为**不可信数据**，不能直接改变工具权限。没有真正的隔离执行环境时，项目只能描述为本地实验系统，不能宣称“生产安全”。

### 4. 学习方法：学 → 跟做 → 迁移 → 独立扩展

这条路线的第一原则是**先学优秀开源作品，再动手写代码**。自己不会的设计，先去成熟项目里看它怎么做；看完再跟做、再变成自己的东西。学习分四级台阶：

1. **学（贯穿全程，占比最大）**：每进入一个新主题，先选一两个优秀开源作品研究它的设计。不是泛读源码，而是带着固定问题去读（见下方“如何读一个开源项目”），产出是一页架构笔记。第 1 个月学 [learn-claude-code](https://github.com/shareAI-lab/learn-claude-code) 和 Aider；之后每进入状态、MCP、RAG、安全、可观测性等主题，先学 DeepSeek Harness、Claude Code、OpenCode、OpenHands 等作品中对应的模块。
2. **跟做（第 1 个月为主）**：以 `learn-claude-code` 为主线教材，一章一章做下来。每章的标准动作是：跑通示例 → 逐行读懂 → **合上教程自己把这一章重敲一遍**（允许回看，不允许复制粘贴）→ 完成一个“改动实验”（改 Prompt、加日志、改工具行为，观察差异）。
3. **迁移（第 1 个月末开始）**：教程是 MIT 许可的，把跟做完成的代码整理、重构成自己的 `agent-lab` 仓库骨架（保留 LICENSE 和出处说明），并在此基础上换上自己的工具、自己的策略命名和自己的测试。
4. **独立扩展（第 2 个月起）**：教程和优秀作品都没覆盖到自己场景的能力——代码库 RAG、评估体系——这时才需要自己设计，但每一步仍然先跑通对应库的官方 quickstart，再动手。

判断标准：**学的阶段看“能不能讲清它为什么这么设计”，跟做阶段看“能不能改得动”，迁移阶段看“能不能讲清每行代码为什么存在”，独立扩展阶段看“能不能为设计取舍写出理由”**。

### 5. 如何读一个开源项目

面对一个几万行的仓库，不要从第一个文件顺着读。固定流程如下，单次研究控制在 3～5 小时：

1. **读 README 和官方文档的架构部分**，回答“它解决什么问题、由哪几个进程/模块组成”；
2. **跑起来**：安装并运行它的最小示例，让它真实工作一次；
3. **找入口**：从 CLI 入口或主函数开始，找到 Agent 循环所在的文件；
4. **跟踪一次调用**：用日志或断点跟踪一次完整请求——输入从哪进、Prompt 在哪组装、模型在哪调用、工具在哪执行、结果怎么回传；
5. **带着固定问题做笔记**：
   - 工具如何注册、Schema 如何定义？
   - 权限和人工确认在哪个层实现？
   - 会话/状态存在哪、如何恢复？
   - 错误、超时、重试怎么处理？
   - 上下文超限时怎么办（截断、摘要、压缩）？
6. **写一页架构笔记**：一张模块图 + “我能借鉴什么、我的项目不需要什么”。

每月末把笔记汇总成一篇源码阅读笔记，这些笔记本身就是面试时讲“我研究过 X 的架构”的证据。

## 二、开始前准备：先通过自测，再进入 20 周

### 1. 入场自测

以下项目都能独立完成，再开始第 1 周：

| 能力 | 通过标准 |
| --- | --- |
| Python | 能写函数、类、异常处理、文件读写和 JSON 处理，并能读懂基础类型标注 |
| 环境 | 能创建虚拟环境或 `uv` 项目，安装依赖，并用 `pyproject.toml` 启动项目 |
| 测试 | 能用 `pytest` 写出至少 3 个带断言的测试，知道测试失败时如何定位问题 |
| 命令行 | 能在终端切换目录、运行脚本、查看进程和读取日志 |
| Git | 能使用 `git status`、`git diff`、分支、提交和回退；知道如何避免把密钥提交到仓库 |
| HTTP | 理解请求、响应、JSON、状态码和超时，能调用一个公开或本地 API |
| SQL | 能完成简单的增删改查，理解表、主键、索引和事务的基本作用 |
| 英文资料 | 能借助词典阅读 README、错误信息和 API 文档，不要求一开始流畅阅读长篇论文 |
| 成本意识 | 知道模型 API 可能产生费用，会设置预算、超时和调用上限 |

不会的内容不要无限扩张补课范围。先补齐上表，再进入主线。

### 2. 预备课程：基础不足时先花 4 周

| 周次 | 内容 | 可验收产出 |
| --- | --- | --- |
| 准备第 1 周 | Python 函数、模块、异常、文件和 JSON | 一个读取配置并处理异常的小工具 |
| 准备第 2 周 | Git、命令行、虚拟环境、依赖管理 | 一个带 README、测试和 Git 历史的小项目 |
| 准备第 3 周 | HTTP、REST、JSON、SQL CRUD | 一个能保存数据并提供简单接口的练习项目 |
| 准备第 4 周 | `asyncio`、超时、pytest、日志 | 一个带异步调用、超时处理和测试的脚本 |

完全初学者可以把准备阶段延长到 6～8 周。准备阶段不学习 LangChain、LangGraph、MCP、多 Agent 或向量数据库；工具越多，越容易把基础问题误判为 Agent 问题。

站内的[前后端开发入门指南](/2026/07/13/fullstack-dev-guide/)和 [FastAPI 后端开发完全指南](/2026/07/14/fastapi-complete-guide/)可以作为基础补课材料，但仍应以代码自测结果为准。

## 三、学习范围：核心、可选与延期

20 周只有约 240～300 小时，必须主动控制范围。下面的分层比“所有技术都学一遍”更可靠。

### 核心轨道

核心轨道必须围绕主项目完成：

- Python 工程化、类型、异常、异步、超时、取消和重试；
- 一个模型供应商的官方 SDK：Streaming、Structured Output 和 Tool Calling；
- 原生工具调用循环、工具 Schema、工具结果和最大轮数；
- 文件读取、代码搜索、固定测试等受限工具；
- 工作区边界、命令 Allowlist、人工审批、审计日志和密钥保护；
- 确定性状态机、Checkpoint、Resume、幂等和失败恢复；
- MCP Server/Client 的基本接入，以及认证、超时和权限边界；
- 代码库摄取、切分、元数据、检索、引用和无证据拒答；
- 固定评估集、人工抽样、回归测试、结构化日志、Docker 和 CI；
- 成本、延迟、失败率和已知限制的记录。

### 优秀开源作品学习计划

以下作品是**学习材料**，已安排进对应周的“先学”环节。原则是学它的设计决策，不把整个项目引入为依赖：

| 作品 | 学什么 | 安排在 |
| --- | --- | --- |
| [learn-claude-code](https://github.com/shareAI-lab/learn-claude-code) | Agent harness 的完整演进：loop、工具、权限、上下文管理 | 第 1 个月跟做主线 |
| [Aider](https://github.com/Aider-AI/aider) | “读代码→改代码→跑测试→继续修”的编辑闭环、Git 集成 | 第 1 周 |
| [Claude Code](https://github.com/anthropics/claude-code) + [官方扩展文档](https://code.claude.com/docs/en/features-overview) | 权限模式、Hooks、Skills、插件如何包装 Agent 能力 | 第 2、13、16 周 |
| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | 插件化架构、工作区与权限设计（预览版，学思想不绑定 API） | 第 5 周 |
| [OpenCode](https://github.com/anomalyco/opencode) | Plan/Build 双模式的写权限隔离、Provider 抽象 | 第 13、16 周 |
| [OpenHands software-agent-sdk](https://github.com/OpenHands/software-agent-sdk) | Agent Runtime、事件流、执行环境的生命周期设计 | 第 14 周 |

其余工具按需对照，不作为学习计划的一部分：

- **LangChain**、**OpenAI Agents SDK**：主线稳定后对照其抽象即可；
- **Langfuse**、**LiteLLM**：第 15 周需要更完整方案时再评估；
- **Redis**：确实出现缓存、队列问题时再学；
- **Qdrant 与 pgvector 的第二种方案**：第一种做出 baseline 后再比较；
- **Dify、RAGFlow**：第 19～20 周带着问题看架构，不用“能部署平台”替代代码能力。

### 延期轨道

以下内容不进入 20 周主线：

- Kubernetes、微服务拆分和复杂消息系统；
- 自建 GPU 推理、模型量化和大规模吞吐优化；
- LoRA、SFT、RLHF 和训练数据工程；
- 多智能体群舞、自动规划和 A2A；
- 复杂多租户、计费、运营后台和企业级合规体系。

如果目标岗位明确要求其中某项，应根据 JD 另开学习路线，而不是把所有内容硬塞进本计划。

## 四、辅助阅读：`learn-claude-code` 应该怎样使用？

[shareAI-lab/learn-claude-code](https://github.com/shareAI-lab/learn-claude-code) 是一个以 Python 逐步构建 Claude Code 类 Agent harness 的开源教程。仓库 README 当前将学习内容组织为约 20 个循序渐进的章节，根目录可见 `s01_*` 到 `s20_*` 等课程目录，涵盖 Agent loop、工具、权限、Hooks、Todo、Subagents、Skills、Memory、Compaction、恢复、后台任务、Worktree、MCP 和综合实现等主题。仓库标注为 MIT 许可证；使用时应以仓库当前目录和许可证文本为准。

**它是第 1 个月的主线教材**，不是补充阅读。每一章都是可以直接运行的小程序，跟做方式是：跑通 → 逐行读懂 → 合上书重敲 → 做改动实验。第 1 个月结束时，把跟做成果整理重构成自己的 `agent-lab` 仓库（保留 LICENSE 与出处），之后所有里程碑都在这个仓库上继续演化。

### 第 1 个月的跟做安排

| 周次 | 跟做章节（按当前目录名，以仓库为准） | 每周改动实验 |
| --- | --- | --- |
| 第 1 周 | Agent loop、工具注册、工具结果相关章节（约 `s01`～`s04`） | 给 loop 加详细日志，画出一次调用的完整链路图 |
| 第 2 周 | 权限、确认、Hooks 相关章节 | 把一个“放行”规则改成“拒绝”，观察系统行为并写测试 |
| 第 3 周 | Todo、任务拆分、Subagents 相关章节 | 只比较拆分方式和通信代价，不默认引入多智能体 |
| 第 4 周 | Skills、Memory、Compaction 相关章节（选做）+ 开始迁移 | 把前 3 周的跟做代码重构成 `agent-lab` 骨架 |

恢复、后台任务、Worktree 和 MCP 章节留到第 7～8 周对照学习。跟做时不要整段复制到自己仓库；迁移阶段引用代码时保留出处和许可证说明。

## 五、一个主仓库与六个里程碑

### 1. 版本路线

整个 20 周只维护一个主仓库：

```text
agent-lab/
├── src/                 # Agent、工具、策略、状态和 API
├── tests/               # 单元、集成和失败路径测试
├── evals/               # 评估任务、标注和运行脚本
├── docs/                # 架构、威胁模型、决策记录
├── docker-compose.yml
├── pyproject.toml
└── README.md
```

阶段性实验可以放在 `experiments/` 或单独的临时目录中，但不以“拥有多少仓库”作为完成标准。

| 版本 | 新增能力 | 主要验收问题 | 计划周次 |
| --- | --- | --- | ---: |
| `v0.1` | 原生模型调用、工具循环、受限读取/搜索/测试、补丁预览 | Agent 如何读代码、提出修改并验证结果？ | 第 3 周 |
| `v0.2` | 插件注册、Schema、策略、Allow/Deny、人工审批 | 哪些操作允许执行，谁能批准高风险操作？ | 第 4 周 |
| `v0.3` | State、Checkpoint、Resume、重试、幂等 | 重启和重试如何避免重复副作用？ | 第 7 周 |
| `v0.4` | 基于既有 Tool 接口的 MCP Server/Client | MCP 是否绕过原有认证、授权和审计？ | 第 8 周 |
| `v0.5` | 代码库索引、检索、引用、无证据拒答 | 如何找到正确代码，如何证明回答有依据？ | 第 12 周 |
| `v1.0` | 评估、观测、成本、部署、README 和演示 | 如何知道系统变差、变慢或变贵？ | 第 20 周 |

每次打 Tag 都必须满足：

1. 上一版本的核心测试继续通过；
2. 新能力通过接口接入，而不是复制一套 Agent Loop；
3. README 写清新增能力、解决的问题、已知限制和引入的代价；
4. 至少有一个可重复运行的成功案例和一个失败案例；
5. 不把实验系统的能力夸大为生产级能力。

### 2. 从第一天开始的安全基线

第一次让 Agent 接触工具前，就建立以下边界：

- 默认只读，只允许在自己拥有或获授权的临时工作区运行；
- 所有路径解析后必须仍位于工作区内，拒绝路径穿越和符号链接绕过；
- 初期只允许固定的测试命令，禁止任意 Shell；
- 文件写入先生成 diff，必须经过人工确认；
- 排除 `.env`、密钥、SSH 配置、生产配置和用户主目录；
- 设置最大轮数、单次超时、取消机制和模型调用预算；
- 模型输出只能提出工具调用，不能直接成为授权决定；
- README、Issue、代码注释中的指令只作为数据，不能覆盖策略；
- 记录工具名、参数摘要、审批结果、耗时和错误，但不要把密钥写入日志。

后续再逐步增加能力：`v0.2` 将策略层独立于模型且 Deny 优先，`v0.3` 处理副作用幂等，`v0.4` 验证 MCP 不绕过权限，`v1.0` 进行安全回归和停止/回滚演示。

## 六、20 周执行计划

每周只设置一个主交付物。遇到阻塞时，优先修复当前交付物，不要借机新增框架。

### 第 1 个月：跟做 `learn-claude-code`，长出项目骨架

这个月不写自己的架构，任务就是**把教材一章章做下来、改得动、讲得清**。主项目在月底从跟做代码中演化出来。

#### 第 1 周：环境 + 跟做 Agent loop 与工具章节

**目标：** 跑通教材，搞清一次 Agent 调用的完整路径。

**具体步骤：**

1. 配好环境：创建 `uv` 或虚拟环境项目，用环境变量读 API Key，配好 `.gitignore`，克隆 [learn-claude-code](https://github.com/shareAI-lab/learn-claude-code)；
2. 按 README 跑通 Agent loop、工具注册、工具结果相关章节（当前约为 `s01`～`s04`，以仓库目录为准）；
3. 每章合上教程重敲一遍，跑通为止；
4. 改动实验：给 loop 加上详细日志（每轮模型返回了什么、调用了哪个工具、结果是什么），重新运行并观察；
5. 画出一次完整调用的链路图：输入 → Prompt 组装 → 模型返回 → 工具执行 → 结果回传 → 循环停止；
6. 有余力时，在玩具仓库里跑一次 [Aider](https://github.com/Aider-AI/aider) 修个小问题，对比它和教材的 loop 有什么异同。

**本周产出：** 可运行的跟做代码、带日志的一次完整调用记录、一张调用链图、3 个针对工具结果解析的测试。

**验收问题：** 循环什么时候停？工具失败时返回什么？模型能不能在一轮里连续调用多个工具？

#### 第 2 周：跟做权限、确认与 Hooks 章节

**目标：** 搞清“模型提出操作”和“系统批准操作”之间的边界。

**具体步骤：**

1. 跟做权限、人工确认、Hooks 相关章节，同样先跑通再重敲；
2. **先学**：读 [Claude Code 官方文档](https://code.claude.com/docs/en/features-overview)中权限与 Hooks 部分，看一个成熟产品如何把权限分层（允许、询问、拒绝）以及 Hooks 在调用链的什么位置介入，写一页笔记；
3. 改动实验：把一个默认放行的规则改成拒绝，观察 Agent 的行为变化，把过程写成测试；
4. 整理一张权限表：哪些操作只读放行、哪些需要确认、哪些永远拒绝；
5. 理解并写下一条原则：**模型输出只是“请求”，策略层才决定“能不能做”**；
6. 补充基础安全概念：工作区边界、路径穿越、命令 Allowlist、密钥与 `.env` 排除（第 3 周迁移时要用）。

**本周产出：** 跟做代码、权限表、放行/拒绝两组行为测试、一页“权限边界”笔记。

**验收问题：** 如果模型直接说“已获批准”，系统会不会被骗过？Hooks 在调用链的哪个位置介入？

#### 第 3 周：跟做任务拆分章节 + 开始迁移出 `agent-lab`

### 第 2 个月：状态、恢复与 MCP

#### 第 5 周：先用确定性状态机表达任务

**目标：** 在引入框架前，先理解状态和流程的业务含义。

**先学：** 读 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 的 README 和架构文档，看一个生产方向的 harness 如何组织会话、工作区、权限和插件（该项目是开发者预览版，学设计思想，不绑定具体 API）。用“如何读一个开源项目”的固定问题做笔记，画出它的模块图。

**学习与实现：**

- 定义任务状态：`分析`、`等待审批`、`修改中`、`测试中`、`需要修复`、`完成`、`失败`；
- 为每个状态定义输入、输出、允许的下一状态和失败处理；
- 将“分析—修改—测试—修复”写成可观察的确定性流程；
- 为状态转换写测试，禁止模型随意改变关键状态；
- 用 SQLite 或文件形式保存最小状态，先不引入 Redis。

**本周产出：** 状态转换图、状态数据结构、状态机测试和 3 个失败路径案例。

**验收问题：** 进程在测试阶段退出后，重启时应该回到哪里？哪些状态可以安全重试？

#### 第 6 周：用 LangGraph 管理显式状态

**目标：** 使用 LangGraph 表达节点、边、条件分支、Checkpoint 和中断，而不是让框架吞掉业务代码。

**先跑通：** 按 [LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/)的 quickstart 运行一个最小 StateGraph 示例，确认 Checkpoint 和中断的行为，再开始改造自己的状态机。

**学习与实现：**

- 将第 5 周的状态转换映射为 State、Node、Edge 和 Conditional Edge；
- 实现中断和人工审批；
- 使用本地 Checkpoint 先验证暂停和恢复，再考虑更复杂的持久化；
- 保留 `agent-lab` 自己的 Tool、Policy 和数据结构；
- 阅读官方迁移文档时注意：当前需要迁移的是旧的 `create_react_agent` Agent 工厂用法，不应笼统写成整个 `langgraph.prebuilt` 命名空间都废弃。

**本周产出：** LangGraph 状态图、一次中断/恢复演示、框架前后行为对照测试。

**验收问题：** LangGraph 负责什么，业务工具和权限策略负责什么？如果移除 LangGraph，哪些业务代码仍然可以运行？

#### 第 7 周：重试、幂等和 Resume，发布 `v0.3`

**目标：** 让失败恢复不产生重复副作用。

**学习与实现：**

- 为任务、工具调用和审批定义唯一 ID；
- 区分可重试错误、不可重试错误和需要人工处理的错误；
- 为写文件、提交补丁等副作用设计幂等策略；
- 测试进程重启、网络超时、重复回调、审批后重试和中断恢复；
- 发布 `v0.3`，附上恢复测试报告。

**本周产出：** `v0.3` Tag、Resume 演示、重试矩阵和至少 4 个恢复/重复写入测试。

**验收问题：** 同一个工具结果到达两次时会发生什么？重试模型请求是否会重复写文件？

#### 第 8 周：接入 MCP，发布 `v0.4`

**目标：** 理解 MCP 是工具和资源的标准化接入方式，而不是替代业务权限的“万能协议”。

**先跑通：** 按 [MCP Python SDK 官方仓库](https://github.com/modelcontextprotocol/python-sdk)和[官方文档](https://py.sdk.modelcontextprotocol.io/)的示例运行一个最小 Server/Client，确认工具列表、调用和返回格式，再把接入点映射到自己的工具层。

**学习与实现：**

- 使用当前稳定的 v2 SDK 线实现一个最小 MCP Server 和 Client，优先从本地 stdio 开始；
- 将已有的代码搜索或测试工具通过 MCP 暴露，而不是重新写一套业务逻辑；
- 至少实现一个 Resource 或结构化工具结果；
- 验证 MCP 接入仍然经过 `agent-lab` 的 Policy、Approval、Timeout 和 Audit 层；
- 对远程 Streamable HTTP、认证和部署只做概念记录，不在本周扩展成平台项目。

**本周产出：** `v0.4` Tag、MCP Server/Client、原生函数工具与 MCP 工具的对照测试、权限边界说明。

**验收问题：** MCP Server 返回的工具是否能绕过本地策略？远程工具超时或返回恶意内容时，Agent 如何停止？

### 第 3 个月：代码库理解与第一个作品集检查点

#### 第 9 周：代码库摄取和增量索引

**目标：** 把代码库转换为可检索、可追踪、可更新的资料。

**学习与实现：**

- 处理 Python、Markdown、配置和测试文件；其他语言先按文本处理；
- 排除 `.git`、`.env`、密钥、构建产物和二进制文件；
- 记录仓库版本、文件路径、语言、符号、行号和更新时间；
- 设计切分策略，尽量保持函数、类和文档段落的边界；
- 支持重复运行和增量更新，不要每次无条件重建所有数据；
- 把 README、Issue 和代码注释中的提示当作数据，并准备最小 Prompt Injection 样例。

**本周产出：** 可重复执行的摄取脚本、元数据 Schema、3 个不同文件类型的索引样例和增量更新测试。

**验收问题：** 一个文件被修改后，如何知道哪些索引需要更新？检索内容中出现“忽略系统规则”的文本时，策略是否仍然有效？

#### 第 10 周：选择一个向量层，完成检索和引用

**目标：** 让 Agent 找到相关代码，并能给出可核查的证据。

**先跑通：** 用所选向量库（[Qdrant](https://github.com/qdrant/qdrant) 或 [pgvector](https://github.com/pgvector/pgvector)）的官方 quickstart 完成一次插入与查询，确认 Embedding、Top-K 和过滤的行为，再接入自己的索引数据。

**学习与实现：**

- 在 Qdrant 和 pgvector 中选择一个深入，另一个只保留比较笔记；
- 完成 Embedding、Top-K、元数据过滤和基础相似度检索；
- 先建立不带重排的 baseline，再把混合检索或 Rerank 作为可选改进；
- 引用文件路径、符号和行号，避免只引用模糊的文档标题；
- 没有足够证据时返回“无法确定”，不要用模型常识填空；
- 记录检索耗时、模型调用和向量存储成本。

**本周产出：** 一组带人工相关性标签的查询、baseline 结果、优化前后对比和引用示例。

**验收问题：** 检索到的内容为什么相关？引用的行号是否真的支持结论？过滤条件是否阻止了越权文档泄露？

#### 第 11 周：建立评估集并进行错误分析

**目标：** 从“感觉回答变好了”变成“能说明哪项指标发生了变化”。

**学习与实现：**

- 编写一组固定的代码库问题，覆盖定位、解释、影响分析和测试修复；
- 将任务划分为开发集和保留集，避免每次只针对熟悉问题调 Prompt；
- 为每个任务记录输入仓库版本、用户问题、允许工具、预期证据和成功标准；
- 区分未召回、召回噪声、上下文丢失、生成错误、引用错误、权限错误和工具失败；
- 对 LLM-as-a-judge 结果进行人工抽样，不能把模型评分直接当作真值。

**本周产出：** 约 20～30 个带人工标签的开发/保留任务、错误分类表、baseline 报告和一次人工盲检。

**验收问题：** 指标变好是因为真正检索变好，还是因为测试题泄露到了 Prompt 或缓存中？

#### 第 12 周：接入 API 和 Docker，发布 `v0.5`

**目标：** 把命令行原型整理为别人可以启动和检查的项目。

**先跑通：** 按 [FastAPI 官方教程](https://fastapi.tiangolo.com/tutorial/)完成一个带路径参数、请求体和自动文档的最小服务（站内 [FastAPI 后端开发完全指南](/2026/07/14/fastapi-complete-guide/)可作中文参考），再把任务接口挂到 `agent-lab` 上。

**学习与实现：**

- 使用 FastAPI 提供任务创建、状态查询、审批和结果读取接口；
- 选择一种持久化方案：小型本地项目可以先用 SQLite，需要多人或并发实验时再使用 PostgreSQL；
- 用 Docker Compose 启动应用和已经选择的向量层；不为了“像生产”而加入 Redis；
- 编写健康检查、环境变量说明、数据库初始化和最小数据导入命令；
- 保留 CLI 入口，方便调试和离线评估；
- 整理第一版简历和项目页面，进行一次目标 JD 匹配检查。

**本周产出：** `v0.5` Tag、Docker 启动说明、API 文档、第一版项目演示和评估报告。

**验收问题：** 新环境能否按照 README 启动？API 错误、任务失败和审批等待是否能被调用方区分？

第 12 周可以开始整理作品集，是否投递应根据目标岗位、个人条件和招聘节奏决定。阶段成果是求职材料的起点，不是“已经达到录用门槛”的证明。

### 第 4 个月：安全、可观测性和可复现性

#### 第 13 周：威胁建模与安全回归

**目标：** 让安全测试成为代码的一部分，而不是 README 中的一句口号。

**先学：** 看两个成熟产品如何做执行隔离——[Claude Code 文档](https://code.claude.com/docs/en/features-overview)的权限与工具审批设计，以及 [OpenCode](https://github.com/anomalyco/opencode) 的 Plan/Build 双模式（只读规划与可写执行分离）。对比它们与自己 `v0.2` 策略层的差异，写一页笔记，再动手补自己的安全案例。

**至少覆盖：**

- Prompt Injection：仓库文件、Issue 或工具结果试图改变系统规则；
- 越权读取：路径穿越、符号链接、敏感目录和跨工作区访问；
- 危险命令：删除、网络外传、修改工作区外文件和无限进程；
- 审批绕过：模型伪造审批结果、重复回调或直接请求内部工具；
- 信息泄露：Key、环境变量、用户数据和内部错误写入回答或日志；
- 重复副作用：重试和恢复造成重复写入或重复提交。

**本周产出：** 威胁模型、约 10 个安全案例、修复前后结果和一份明确的非目标清单。

#### 第 14 周：结构化事件、Trace 和延迟基线

**目标：** 能从一次失败回答追踪到检索、Prompt、模型、工具和错误。

**先学：** 读 [OpenHands software-agent-sdk](https://github.com/OpenHands/software-agent-sdk) 的文档或源码中事件与生命周期相关部分，看一个生产方向的 Agent SDK 如何定义事件类型、组织事件流；对比自己的结构化日志缺了哪些字段，再动手补。

**学习与实现：**

- 为任务、Agent 节点、模型调用、检索和工具调用定义事件 ID；
- 记录开始/结束时间、状态、错误类别、Token 和成本（能取得时）；
- 用 JSON 日志或 OpenTelemetry 兼容字段组织事件；
- 统计单步和完整任务的 P50/P95 延迟，明确并发、缓存和模型条件；
- 只记录必要的输入摘要，避免把敏感原文复制到日志。

**本周产出：** 一次失败任务的完整追踪图、延迟基线和日志脱敏测试。

#### 第 15 周：模型适配、预算与可选工具对比

**目标：** 让模型可以替换，让成本和失败策略可解释。

**学习与实现：**

- 统一不同模型供应商的请求、结构化输出、工具调用和错误类型；
- 为简单分类、摘要或路由任务设置预算和低成本模型选项；
- 区分网络重试、模型重试和 Agent 任务重试；
- 记录单任务调用次数、输入输出 Token、延迟和成本；
- 有余力时，对比 [LiteLLM](https://github.com/BerriAI/litellm)、[Langfuse](https://github.com/langfuse/langfuse) 或 [OpenAI Agents SDK](https://github.com/openai/openai-agents-python) 的一项能力；
- 只写当前实际验证过的内容，不根据旧教程猜测 API。

**本周产出：** Provider Adapter、预算策略、模型对比记录和成本表。可选工具没有完成，不影响核心路线通过。

#### 第 16 周：CI、复现和有限压测

**目标：** 证明项目能在新环境启动，并知道当前系统的容量边界。

**学习与实现：**

- CI 中运行格式检查、类型检查（如果使用）、单元测试、集成测试和安全测试；
- 验证 Docker Compose 在干净环境中的启动与停止；
- 只做有限并发基线，例如 1、5、10 个任务，记录成功率、P95 和成本；
- 评估模型限流、向量检索、数据库和工具执行分别受什么限制；
- 判断是否需要隔离执行环境；如果没有真正的 Sandbox，不启用“自动执行任意命令”的演示；
- **先学后做**：对比 [Claude Code 的插件机制](https://code.claude.com/docs/en/plugins)与 [OpenCode](https://github.com/anomalyco/opencode) 的 Provider/Tool 设计，回答“能力如何被发现、安装、隔离”，然后据此决定自己的插件层是否还需要补什么。

**本周产出：** CI 配置、复现记录、有限压测报告和“当前不能保证什么”的列表。

- 威胁模型、评估集、模型与 Prompt 版本；
- Docker 启动方式、环境变量和成本预算；
- `v1.0` 必须满足的硬门槛。

**本周产出：** 一页 PRD、一组架构图、一份发布检查表和最终两周修复排期。

#### 第 18 周：打通端到端流程并修复最高优先级失败

**目标：** 在固定范围内完成“提出任务—检索—计划—审批—修改—测试—反馈”的完整路径。

优先处理以下问题：

1. 会导致权限违规或敏感信息泄露的问题；
2. 会造成重复写入、任务丢失或无法恢复的问题；
3. 会使引用错误、无证据回答或测试结果被误判的问题；
4. 才是体验、速度和代码重构问题。

**本周产出：** 端到端演示、失败 Top 5 及其修复记录、回归测试。

#### 第 19 周：发布前回归与可选开源贡献

**目标：** 在发布前用同一份数据重新运行系统。

- 运行软件测试、评估任务和安全案例；
- 对比 baseline 与最终版本，记录成功率、引用正确性、P95、成本和失败类型；
- 人工抽样检查 LLM judge 的误判；
- 检查密钥扫描、依赖、日志、Docker、README 和许可证；
- 可选阅读 [Dify](https://github.com/langgenius/dify)或 [RAGFlow](https://github.com/infiniflow/ragflow) 的相关架构；
- 如果发现真实、可复现且有价值的问题，可以提交文档、测试或 Issue；不要为了完成计划而提交低质量贡献。

**本周产出：** 发布候选报告、限制列表和最终演示脚本。

#### 第 20 周：发布 `v1.0` 与求职材料

只有通过发布硬门槛，才打 `v1.0` Tag。README 至少包含：

- 要解决的问题、用户和非目标；
- 架构图、关键取舍和数据流；
- 本地启动、环境变量和测试命令；
- 评估集说明、指标定义、baseline、结果和失败案例；
- 权限、安全边界、已知漏洞和不能保证的场景；
- 任务成本、延迟、模型版本和运行日期；
- 5 分钟演示脚本和后续改进方向。

**本周产出：** `v1.0` Tag、README、5 分钟演示、项目简历描述和一份 15 分钟架构讲解提纲。

## 七、评估口径：不要把测试数量写成能力证明

### 1. 四类数据要分开

| 名称 | 定义 | 例子 |
| --- | --- | --- |
| 软件测试 | 带可执行断言，验证代码行为 | 工具参数错误时返回错误；路径越界被拒绝 |
| 评估任务 | 有输入、预期标准和评分方法的 Agent 任务 | 根据 Issue 找到相关函数并给出正确引用 |
| 安全案例 | 专门验证攻击和越权路径的场景 | README 诱导 Agent 读取 `.env` |
| 基准运行 | 在固定条件下重复运行，用于比较版本 | 同一评估集、同一模型和 Prompt 的 baseline/最终版对比 |

一个评估任务可能包含多个软件测试，但两者不能在简历和报告中混称。

### 2. 建议指标

- **Task Success**：满足预先定义的完成标准、测试通过且没有权限违规的任务数 ÷ 总任务数；
- **Tool Success**：工具调用成功并返回可用结果的调用数 ÷ 工具调用总数，需区分参数错误和外部依赖错误；
- **Hit@k / Recall@k**：人工标注的相关证据是否出现在前 `k` 个结果中；
- **Citation Coverage**：关键结论中有证据支持的比例；
- **Citation Correctness**：引用路径、符号和行号是否真的支持结论；
- **Groundedness**：回答是否能由提供的检索证据支持；可由人工抽样或辅助评审判断；
- **P50/P95 Latency**：必须注明是单次 API、单个节点还是完整任务，并固定并发、缓存和模型条件；
- **Cost per Task**：明确模型价格日期、输入输出 Token、调用次数和是否包含 Embedding/重排成本；
- **安全失败率**：攻击案例中发生越权、密钥泄露或危险执行的比例，Critical 失败不能被其他指标抵消。

LLM-as-a-judge 可以提高抽样效率，但不是自动真值。至少保留一部分人工盲检，记录评审标准、模型、Prompt 和分歧案例；对于随机性明显的任务，应重复运行并报告波动范围。

### 3. 渐进式建议目标

数量只是组织工作量的参考，不是获得 Offer 的证明：

| 阶段 | 建议目标 |
| --- | --- |
| `v0.1` | 至少 10 个软件测试、5 个最小评估任务 |
| `v0.2` | 至少 20 个软件测试、10 个安全案例 |
| `v0.3` | 覆盖中断、重启、超时、重试和重复写入 |
| `v0.5` | 约 20～30 个有人工标签的代码库检索任务 |
| `v1.0` | 约 40～60 个固定评估任务、约 20 个安全案例、至少 50 个可执行测试 |

如果样例质量不足，宁可少做，也不要为了凑出“100+”而复制相似问题。

### 4. 发布硬门槛

以下项目必须全部满足：

- 核心成功、失败和恢复路径通过测试；
- 没有把 API Key 或私密数据提交到仓库；
- 工具路径、命令、审批和 MCP 权限边界有测试；
- 评估报告能够在固定条件下复现；
- README 写明限制、已知失败和未实现的安全能力；
- Docker 或本地启动步骤能由新环境执行；
- 5 分钟演示不会访问未经授权的真实代码和数据。

架构整洁、P95 优化、完整 Trace、漂亮前端和开源贡献属于加分项，不能替代安全硬门槛。

## 八、每周时间安排与复盘

以每周 14 小时为例：

| 工作 | 时长 | 说明 |
| --- | ---: | --- |
| 主项目开发 | 6 小时 | 只围绕当周交付物 |
| 优秀作品与官方文档学习 | 2.5 小时 | 当周“先学”环节：读设计、跑示例、写架构笔记 |
| 软件测试与评估 | 2 小时 | 包括失败路径、数据和报告 |
| 算法与数据结构 | 1.5 小时 | 2～3 道有复盘的题，不追求盲目刷量 |
| LLM 原理与口述 | 1 小时 | 结合当周项目解释 Token、Attention、KV Cache 或 ReAct |
| README、求职材料与缓冲 | 1 小时 | 记录决策、失败和下一周调整 |

每周日回答以下问题：

1. 本周新增的可运行产物是什么？
2. 哪一个指标变好，分母和实验条件是什么？
3. 一个可复现的失败是什么，下一步如何定位？
4. 哪些内容只是看过，尚未由代码或测试验证？
5. 本周是否新增了不必要的依赖？如果删掉它，主项目是否仍然成立？

### 算法和 LLM 原理的最低节奏

算法是求职准备的一部分，但不应把“中等题 30 分钟内全部无 Bug”写成绝对承诺。建议按目标岗位调整：

- 第 1～4 周：数组、字符串、哈希、栈、队列、双指针；
- 第 5～8 周：链表、二叉树、二分、排序、堆；
- 第 9～12 周：图、BFS/DFS、回溯、贪心；
- 第 13～16 周：动态规划、并查集、前缀和和常见设计题；
- 第 17～20 周：按目标公司的题型做限时模拟和错题复盘。

每道题记录思路、复杂度、错误原因和一次重做结果。LLM 原理至少能够结合项目讲清：Token 和上下文窗口、Transformer/Attention 的基本数据流、KV Cache 的作用、采样参数、Embedding 与检索的关系，以及 ReAct/Tool Calling 与普通文本生成的差别。

## 九、遇到问题时，按卡点补课

| 现象 | 优先补什么 | 暂时不要做什么 |
| --- | --- | --- |
| 工具参数经常错误 | JSON Schema、Pydantic、结构化日志、参数校验 | 立刻更换 Agent 框架 |
| Agent 无限循环 | 最大轮数、状态转换、停止条件、失败分类 | 添加更多工具 |
| 文件访问越权 | 路径规范化、工作区边界、Allow/Deny、审批 | 开启自动执行全部命令 |
| 重试造成重复写入 | 幂等键、事务、状态持久化、回滚 | 增加多 Agent |
| RAG 找不到代码 | 摄取日志、切分、元数据、Hit@k、错误分类 | 先微调模型 |
| 回答有引用但不支持结论 | 行号记录、引用校验、人工抽样 | 只提高 Top-K |
| 服务卡顿 | 超时、并发上限、P95、缓存基线 | 直接上 Kubernetes |
| 费用不可控 | Token 统计、预算、模型路由和调用上限 | 自建 GPU 集群 |
| 问题无法定位 | 结构化事件、Trace、请求 ID、保留失败输入 | 先做复杂前端 |
| MCP 接入后权限失效 | 复用 Policy、认证、审计和超时 | 把 MCP 当作信任边界 |

## 十、如何把项目写进简历和面试材料

### 1. 简历只写真实实现

下面是表达模板，所有 `X`、`Y` 和指标都必须替换成真实实验数据，不能为了好看虚构：

```text
设计并实现基于 Python、FastAPI 和 LangGraph 的代码库分析与测试修复 Agent；
实现受限文件/搜索/测试工具、MCP 适配、人工审批、幂等恢复和引用校验；
在固定的 X 条评估任务上，将任务成功率从 X% 提升至 Y%，并记录 P95 延迟为 X ms；
通过工具 Allow/Deny、工作区边界和 Prompt Injection 回归测试，识别并修复 X 类安全失败；
使用 Docker 复现项目，报告单任务调用次数、模型、Token 和成本口径。
```

如果没有实际测量，就写“实现了测试和统计脚本”，不要写“降低了 X%”或“达到生产级”。

### 2. 第 12 周可以做什么？

第 12 周完成 `v0.5` 后，可以：

- 整理一版针对目标 JD 的简历；
- 录制一个只展示授权测试仓库的短演示；
- 请他人按照 README 启动项目并记录反馈；
- 根据目标岗位要求决定是否开始投递或继续补齐短板。

尽早获得岗位反馈通常比等待项目“完美”更有信息量，但投递本身不是本路线的硬性验收项，也不能据此推断项目已经达到录用标准。

### 3. 面试中必须能回答的问题

- 为什么先写原生 Tool Calling 循环，而不是一开始使用 Agent 框架？
- Tool、Policy、Approval、State 和 MCP 分别解决什么问题？
- 为什么文件和 Issue 中的自然语言不能直接改变权限？
- 进程重启、网络超时和重复回调时，如何保证幂等？
- 代码库 RAG 的切分、元数据、过滤和引用如何设计？
- Recall@k、引用正确率、Task Success 和 Groundedness 分别怎么测？
- 一次任务的 P95 和成本如何定义，实验条件是什么？
- 为什么没有 Sandbox 时不能把任意命令执行称为生产安全？
- 如果删掉 LangGraph、LiteLLM 或 Langfuse，系统的哪些能力仍然成立？
- 一个失败案例如何从日志追踪到模型、检索、工具或权限层？

### 4. 阅读岗位 JD 的方法

投递前逐个阅读当前招聘页面，重点确认：

- 岗位属于应用开发、Agent 平台、评测、安全、Infra 还是算法方向；
- 是否要求 Python 以外的 Java、Go 或其他语言；
- 是否要求 RAG、Tool Calling、MCP、评估、后端、数据库或模型训练；
- 学历、毕业年份、实习时长、地点和到岗要求是否匹配；
- 算法笔试、系统设计、LLM 原理和项目深挖各占什么比重。

招聘市场和技术栈变化很快，本文不使用没有原始链接和统计方法的“某技术出现在多少岗位”结论。项目能证明做过什么，不能替代岗位要求、笔试和面试表现。

## 十一、常见误区

- 不要同时学习 LangGraph、CrewAI、AutoGen、Semantic Kernel 等多个 Agent 框架；
- 不要把部署 Dify 或 RAGFlow 当成理解 RAG 和 Agent 工程的证明；
- 不要在权限、测试和停止机制之前开放任意 Shell；
- 不要把模型输出直接当作授权决定；
- 不要把 README、Issue 或代码注释中的提示当成可信系统指令；
- 不要同时深入 Qdrant 和 pgvector，先用一个做出 baseline；
- 不要在没有真实数据时填写简历指标；
- 不要为了凑开源贡献数量提交低质量 PR 或 Issue；
- 不要把本地实验系统称为生产级或生产安全；
- 不要为了追逐模型新闻频繁重写项目，Provider Adapter 应隔离变化；
- 不要把测试用例数量、GitHub Star 数或框架数量当成能力本身；
- 不要把“完成五个月计划”理解为获得 Offer 的充分条件。
