> 写给零基础的你：不装、不跳步、不拽术语。每个概念先用生活例子讲透，再上命令。
> 读完这一篇，你能看懂 Git 90% 的日常操作，并且知道每个操作背后到底发生了什么。

---

## 开场：你一定干过这件事

写一份重要文档，改着改着，文件夹里就变成了这样：

- `报告.docx`
- `报告-最终版.docx`
- `报告-最终版2.docx`
- `报告-打死也不改了版.docx`
- `报告-真·最终·再改是狗版.docx`

而且三天后你已经忘了"最终版2"和"打死也不改版"到底差在哪。

更崩溃的场景：同事也改了这份文档发给你，你们俩手里各有一个"最终版"，里面的内容还不一样，只能瞪着眼睛一段一段对比。

**Git 就是为了终结这种混乱而生的。**

---

## 一、Git 是什么：一台"文件时光机"

一句话定义：**Git 是一个版本控制工具，它帮你记住文件每一次改动，随时可以穿越回任何一个历史时刻。**

拆开解释：

- **版本控制（version control）**：不是只保存"最新的样子"，而是保存"每一次变化的历史"。就像游戏存档不是一个栏位而是无限栏位。
- **谁改的都记着**：每一次改动都带着作者、时间、备注。团队协作时再也不用猜"这行代码是谁写的、为啥这么写"。
- **分布式**：每个参与者的电脑上都有一份**完整的**历史账本，不依赖某台中心服务器。这点后面讲远程仓库时再细说。

Git 是程序员的世界标准，但本质上它管理的就是"一堆文件的变化历史"，文档、配置、笔记都能管，只是管纯文本代码最拿手。

---

## 二、仓库（Repository）：装了时光机的文件夹

被 Git 管理的那个文件夹，就叫**仓库**，英文 repository，大家平时直接喊 **repo**。

一个仓库 = 两种东西：

1. **你能看到的文件**：代码、文档，你日常编辑的那些。
2. **一个隐藏账本**：文件夹深处有个叫 `.git` 的隐藏文件夹，里面记着这个仓库自出生以来的全部历史、全部分支、全部设置。

**这个 `.git` 账本就是时光机的核心。** 你把 `.git` 删了，文件夹瞬间变回普通文件夹，所有历史灰飞烟灭；反过来，只要 `.git` 还在，哪怕你把外面的文件全删了，也能一个命令全部恢复。

获得一个仓库只有两条路：

```bash
git init      # 给现有文件夹"开光"：就地创建一个 .git 账本
git clone 网址  # 从云端把别人已有的仓库整个复制一份下来
```

## 三、提交（Commit）：游戏存档点

你改完一些东西，觉得"这个阶段性的东西值得记下来"，就让 Git 拍一张**快照**——这个动作叫 **commit（提交）**，拍出来的快照就是一个**存档点**。

几个要点：

- **Git 存的是"快照"，不是"差异"**。每张存档都是当时整个项目的完整面貌（内部有压缩优化，不会真的复制几十份，你当它是完整快照理解就行）。
- **每个存档点有个全球唯一的编号**，叫 **hash（哈希值）**，长得像 `a1b2c3d9...` 这样一串乱码。它是这张存档的"身份证号"。
- **每次提交必须写一句备注**（commit message），说清楚这次干了什么。好习惯是写"修复了登录按钮点击无反应"，而不是"update"——三个月后翻历史时你会感谢自己。
- **存档点连成一条线，就是历史**。沿着这条线可以随时"读档"回到任何时刻。

```bash
git commit -m "修复了登录按钮点击无反应"
```

## 四、三个区域：新手的第一道坎

这是 Git 里最反直觉、但必须先迈过去的坎：**从"你改文件"到"存档完成"，中间隔着三个区域。**

| 区域 | 官方名 | 大白话 | 类比（拍照） |
|---|---|---|---|
| 工作区 | Working Directory | 你实际看到、正在编辑的文件 | 舞台，演员随便走位 |
| 暂存区 | Staging / Index | 一个"候场名单"，决定这次存档收录哪些改动 | 候场区，点谁谁准备入镜 |
| 仓库 | Repository | 账本，存档的最终归宿 | 相册，快门按下去就成了 |

对应的两个动作：

```bash
git add 文件名     # 把这个文件的改动放进"候场区"（暂存）
git commit -m "…"  # 按快门：把候场区里的改动拍成一张存档，记进账本
```

**为什么非要多个"候场区"，直接存档不行吗？**

因为你常常一次改了 10 个文件，但逻辑上是两件事：3 个文件在修 bug，7 个文件在写新功能。有了暂存区，你就可以：

- 先把 3 个 bug 文件 `add` → `commit`（存档一：修 bug）
- 再把 7 个功能文件 `add` → `commit`（存档二：新功能）

历史清清爽爽，一条存档干一件事。没有暂存区，就只能"一锅烩"地存。

另外两个命令：

```bash
git add .      # 把当前所有改动全部放进候场区（懒人用法）
git status     # 仪表盘：随时查看三个区域现在是什么状态
```

**`git status` 是你最好的朋友**，任何时候搞不清状况，先敲它。它会告诉你：哪些文件改了没暂存、哪些已暂存待提交、当前在哪条分支上。

### 候场区进阶：放进购物车还能拿出来吗？

实际干活时特别常见的场景：你陆陆续续 `git add` 了 A、B、C 三处改动，临存档前突然觉得"A 还不成熟，这次别带上它"。能单独把 A 请出去、B 和 C 留下吗？分两种情况：

**情况一：A、B、C 是三个不同的文件 —— 可以，一条命令的事**

```bash
git restore --staged A.txt
```

A 被请出候场区，B、C 原封不动留在里面。注意 A 的修改**并没有丢**，只是从"本次存档名单"里划掉了，文件还是你改过的样子。购物车里的东西本来就该随便拿进拿出，`commit`（结账）之前一切都不算数。

**情况二：A、B、C 是同一个文件里的三处改动 —— 默认不行**

因为 `git add 文件名` 添加的是"这个文件此刻的整体状态"，而不是单独某一处改动：你第二次 add 时，文件里已经含着改动 A，进候场区的就是 A+B；第三次就是 A+B+C——三处改动在候场区里已经揉成一团，没法单独剔出 A。

想精确到"同一个文件里只存档某几处改动"，要用补丁模式：

```bash
git add -p 文件名
```

Git 会把文件里的改动拆成一小块一小块（叫 hunk），逐块问你"这块要不要入镜？y/n"，你挑着选就行。

**顺带把"add 到底必不必须"说透**：确实有偷懒命令 `git commit -a`，能跳过 add、把所有改动一锅烩直接存档。但一锅烩恰恰是 add 要拯救的东西——你一下午改了 10 个文件，里面混着"修 bug"和"写新功能"两件事，有了 add 才能拆成两次清清爽爽的存档。所以记住：**add 的价值不在"能不能"，在"分得开"。**

## 五、分支（Branch）：平行故事线

你在写小说，写到一半突发奇想："要是让主角黑化会怎么样？"但不确定好不好，不想毁掉现在的稿子。

**开一条分支（branch）**：从当前存档点复制出一条平行的创作线。

```
主线 main:  第1章 → 第2章 → 第3章 → 第4章（主线继续正常更新）
                              ↘
试验分支:                     第3章改 → 主角黑化 → ...
```

- **主线（默认叫 main，老仓库叫 master）**保持原样，安安全全。
- 你在试验分支上随便折腾：折腾好了，把这条线**合并（merge）**回主线；折腾砸了，整条扔掉，主线毫发无损。

**分支的本质**（知道这个你就不怕它了）：分支不是什么沉重的复制，它只是**一张指向某个存档点的便签纸**，上面写着分支名。开分支 = 贴一张新便签，成本几乎为零。所以 Git 圈有句名言："分支随便开，不要钱。"

分支命名是习惯不是规定，常见套路：

- `feature/登录功能`：开发新功能
- `hotfix/支付崩溃`：紧急修复线上 bug
- `bugfix/头像不显示`：修普通 bug

```bash
git switch -c feature/登录功能   # 从当前位置长一条新分支，并跳过去
git switch main                 # 跳回主线（切换时文件内容会"哗啦"换成那边的样子）
```

## 六、HEAD：写着"你在这"的箭头

仓库里有几十张"分支便签"，Git 怎么知道你此刻正在哪条线上干活？

靠一张特殊的便签，叫 **HEAD**——它就相当于地图上的**"你在这"**红色箭头。

- HEAD 指向哪个分支，你就在哪个分支上；你看到的文件就是哪个分支的内容。
- 你每做一次 commit，**当前分支的便签往前挪一格**（指向新存档），HEAD 跟着一起走。
- 看不懂 Git 提示的时候，先问自己一句："我的 HEAD 现在指在哪？"大半的迷茫就消了。

（进阶彩蛋：HEAD 也可以直接指向某个存档点而不是分支，那叫"分离 HEAD"状态，相当于只穿越回去参观、不在任何线上。新手知道有这么个词就行。）

## 七、合并（Merge）与冲突（Conflict）

### 合并：两条故事线合成一条

试验分支折腾满意了，要把成果并回主线：

```bash
git switch main              # 先跳回主线
git merge feature/登录功能    # 把那条线"吸"进来
```

顺利的话 Git 自动完成，两线的改动合体，生成一个新的存档点。

### 冲突：Git 在"请示领导"

但如果你和同事**改了同一行代码**，改成两个不同的样子，Git 傻眼了：两个版本都对，该听谁的？

**它不替你做主，而是把两个版本都摆出来，让你亲自拍板**——这就是冲突（conflict）。文件里会出现这样的标记：

```
<<<<<<< HEAD
主线上写的是：按钮是蓝色
=======
分支上写的是：按钮是红色
>>>>>>> feature/登录功能
```

解决冲突三步走：

1. **手动编辑**：把标记删掉，留下你要的内容（蓝色、红色、或者干脆改成绿色）。
2. `git add` 这个文件：告诉 Git "这处我定好了"。
3. `git commit`：完成合并存档。

记住：**冲突不是错误，不是电脑坏了，是 Git 在向你请示**。心态放平，看清楚两边各写了什么，选一个就行。

## 八、远程仓库：GitHub 是啥，push / pull 是啥

到现在为止，一切还只发生在你自己电脑上。可你电脑要是坏了呢？要和同事协作怎么办？

**远程仓库（remote）= 放在云端服务器上的同一本项目账本**。它有两个作用：

1. **保险柜**：本地电脑炸了，云端还有完整历史。
2. **协作广场**：所有参与者都往这儿同步，大家的劳动在这里汇合。

**GitHub、Gitee（码云）就是托管远程仓库的网站**，相当于"账本银行"。注册账号，就能免费存放你的远程仓库。

### 几个必须认识的关键词

- **origin**：你的远程仓库的默认"外号"。一个本地仓库可以连好几个远程，第一个通常就叫 origin（就是"起源"的意思，只是个名字，别想复杂了）。
- **clone（克隆）**：把云端的仓库**整店复制**一份到你电脑上，连文件带完整账本。
- **push（推送）**：你本地攒了几个新存档，`git push` 把它们**寄到云端**去。没 push 之前，你的提交只有你自己看得见。
- **fetch（抓取）**：只把云端的最新情况**下载下来看一眼**，不动你正在编辑的文件。像快递到了先放驿站。
- **pull（拉取）= fetch + merge**：把云端的新存档拿下来，并且**直接合并**进你当前的分支。像取快递顺便当场拆开用掉。

### 回到"分布式"这个词

集中式工具（老一辈的 SVN）是"账本只在中央服务器上"，断网就抓瞎。Git 是**每台电脑都有完整账本**：断网时你照样能 commit、开分支、看历史，联网后再 push 同步。云端服务器挂了，随便找台同事的电脑就能把完整历史恢复出来——**每个人都是备份**。

## 九、Stash：把半成品塞进抽屉

经典窘境：你正在新功能分支上改到一半，代码还是乱的，突然要切去别的分支处理急事。不想提交半成品，又不想丢掉。

**`git stash` = 拉开抽屉，把当前没提交的改动整个塞进去**，工作区瞬间干净，你随便切分支办事。

```bash
git stash        # 塞进抽屉
git stash list   # 看看抽屉里压了几层
git stash pop    # 倒出最上面一层，接着干
```

它好用在快；缺点是没标签、容易忘（塞了三层就忘了每层是啥）。所以它是**应急工具，不是收纳方案**。

## 十、Worktree：一个仓库，多张书桌

这是本文的"高级甜点"，也是很多人用了就回不去的功能。

### 它解决什么问题

一个普通仓库文件夹，**同一时刻只能摊开一条分支**。想换分支就得切换（switch），可切换的代价不小：半成品要收起来、依赖要重装、编辑器要重新加载、新旧两个版本没法同时跑起来对比。

### 一句话定义

> **Worktree（工作树）：让同一个仓库在硬盘上开出好几个文件夹，每个文件夹摊开一条不同的分支，同时干活，互不干扰。**

用法：

```bash
git worktree add ../我的项目-修bug -b hotfix   # 旁边开个文件夹，新建 hotfix 分支摊开
git worktree add ../我的项目-对比旧版 v1.0      # 也可以摊开已有的分支或标签
git worktree list                             # 看看现在有几张"书桌"
git worktree remove ../我的项目-修bug           # 用完正确拆除
git worktree prune                            # 手动删过文件夹的话，扫扫地
```

### 必须捋清的关系（精华）

- **所有工作区共享同一本 `.git` 账本**。在任何一张书桌上做的提交，记在同一本账上，别处随时能用。
- **分支是"内容"（虚拟的，存在账本里）；工作区是"容器"（物理的文件夹）**。内容是永久的，容器随用随扔——删掉工作区文件夹，提交一个都不会少。
- **一张书桌同一时刻只摊开一条分支；一条分支同一时刻只能摊在一张书桌上**（Git 强制，防止两张桌子同时改同一条线改乱了）。
- **分支可以完全不摊开**：账本里躺着几十条旧分支，大多数都没有自己的工作区，需要时再开桌。
- **开工作区不强制开新分支**：可以摊开已有分支（`git worktree add 路径 main`），也可以顺便新建（加 `-b`）。
- **多张书桌的成果可以合并**：你在 A 书桌的 hotfix 分支修 bug，在 B 书桌的 feature 分支写功能，最后各自 commit，再 merge 回 main 主线——这正是分支存在的意义。

### 典型场景

- 线上着火了，开发一半的功能原封不动，旁边开桌修 bug；
- 新旧两个版本同时运行，左右开弓对比效果；
- 长测试跑 20 分钟？这张桌子晾着，去另一张桌子继续写代码；
- 让 AI 编程助手并行干多个任务，各占一张书桌，互不踩踏。

## 十一、.gitignore：账本的黑名单

不是所有文件都值得记账。比如：

- **依赖包文件夹**（如 `node_modules`）：几万个小文件，体积巨大，而且一条命令就能重新下载，记账纯属浪费；
- **密码、密钥、配置文件**：记进账本再 push 到云端 = 把家门钥匙贴在小区门口；
- **系统垃圾文件**（Windows 的 `Thumbs.db`、macOS 的 `.DS_Store`）、编辑器缓存、编译产物。

解决办法：在仓库根目录建一个名叫 `.gitignore` 的纯文本文件，一行一条"拉黑规则"：

```
node_modules/
*.log
.env
Thumbs.db
```

Git 从此对这些文件视而不见，`git status` 里也清净了。

**注意**：`.gitignore` 只能拉黑"还没入过账"的文件。如果一个文件以前已经被 commit 过，光拉黑没用，得先 `git rm --cached 文件名` 把它从账本上除名（本地文件保留），之后再拉黑才生效。

## 十二、后悔药三件套：restore / reset / revert

"改错了怎么办"是新手最大的焦虑。Git 的好处是**几乎永远有后悔药**，但要分场景吃对药：

| 场景 | 吃哪颗药 | 大白话解释 |
|---|---|---|
| 文件改乱了，**还没 add** | `git restore 文件名` | 把这次的涂鸦扔掉，恢复成上次存档的样子 |
| **add 错了**，不该入镜的进了候场区 | `git restore --staged 文件名` | 把它请出候场区，改动本身还在，不丢 |
| **commit 错了**，还没 push，只有自己知道 | `git reset` | 把分支便签往回拨，假装那次存档没发生 |
| **commit 错了，而且已经 push 了**，别人可能已基于它干活 | `git revert` | 不撕历史，在后面补一张"反向操作"的存档来抵消 |

重点区分后两颗（新手最容易踩的坑）：

- **reset = 撕掉账本最后几页**。干净利落，但属于**改写历史**。如果那几页已经 push 到云端、别人已经看过甚至基于它继续写了，你撕了就会天下大乱。所以铁律：**只 reset 自己还没 push 的提交**。
  - 它有三个档位：`--soft`（最温柔，只撤存档，改动全部保留在候场区）、`--mixed`（默认，改动退回工作区）、`--hard`（核弹，改动直接抹掉，慎用！）。
- **revert = 在账本后面补一页，写"上次那页作废"**。历史一页不撕，只是加一张反向存档把那次改动抵消掉。安全、体面，**已经 push 的错误提交，一律用 revert**。

### 终极底牌：git reflog

就算你 reset 错了、分支删错了，也别慌。`git reflog` 是账本的**监控摄像头**：你的 HEAD 去过的每一个位置都记录在案。跟着它，九成九的"完蛋了"都能找回来。

### 顺带的超能力：随时跳回任何一个存档点

"版本 1 → 2 → 3 → 4，我能直接从 4 跳回 2 吗？"——太能了，这正是时光机的主业。先记住一个让人安心的大前提：**跳回 2 不会删掉 3 和 4**，它们好端端躺在账本里，你随时能再跳回来。"穿越"和"删除"是两回事。

具体怎么跳，看你想干嘛：

| 你想干嘛 | 命令 | 大白话 |
|---|---|---|
| 只是回去**看看** 2 长什么样 | `git switch --detach 版本2的编号` | 时光机参观模式，看完 `git switch main` 回到现在 |
| 想**从 2 重新出发** | `git switch -c 新分支 版本2的编号` | 从 2 长一条新故事线，3、4 留在原线不动 |
| **彻底不要 3 和 4 了**（且没 push） | `git reset --hard 版本2的编号` | 撕掉账本最后两页，回到 2 |
| 3 和 4 有错、**已经 push 了** | `git revert` 对应提交 | 不撕账本，在后面补"反向存档"抵消 |
| **只要 2 里面的某一个文件** | `git restore --source=版本2的编号 文件名` | 只把那个文件捞回 2 的样子，其他不动 |

版本编号就是每个存档的 hash（用 `git log` 查）；打过 tag 的话直接用 `v2` 这种名牌更人性化。日常最推荐前两行——**先回去看看，满意了就开条新分支从那儿接着走**，全程不动原来的历史，最稳。

## 十三、Tag：给重要存档点贴金边名牌

存档点有成百上千个，编号都是 `a1b2c3d` 这种乱码。"去年发布的 1.0 版到底对应哪个存档？"没人记得住。

**Tag（标签）就是给重要存档点钉上一块永久的金边名牌**：

```bash
git tag v1.0.0      # 给当前存档钉上 "v1.0.0" 的名牌
```

区分一下它和分支：

- **分支是会挪动的便签**：你每 commit 一次，它就往前挪一格。
- **Tag 是钉死的纪念牌**：一旦钉上，永远指向那个存档，雷打不动。

所以 tag 的典型用途就一个：**标记正式发布过的版本**（v1.0、v2.3.1……），以后随时能精确回到"发布那一刻"的样子。

## 十四、日常命令地图：90% 的日子就靠这几句

```bash
# —— 每天开工 ——
git pull                          # 把云端最新成果拿下来合并

# —— 开始一件新任务 ——
git switch -c feature/新功能       # 从主线长一条新支线，跳过去

# —— 干活循环（一天重复 N 次）——
改文件……
git status                        # 看仪表盘：改了啥、暂存了啥
git add 文件名                     # 挑选本次要存档的改动入候场区（git add . 全选）
git commit -m "写清楚这次干了啥"    # 按快门存档

# —— 收工同步 ——
git push                          # 把本地新存档寄到云端

# —— 支线完工 ——
git switch main                   # 跳回主线
git pull                          # 确保主线是最新的
git merge feature/新功能           # 把支线成果并进来（可能遇冲突，手动裁决）
git push                          # 合并结果寄到云端

# —— 应急 ——
git stash / git stash pop         # 半成品塞抽屉 / 倒出来
git worktree add ../修bug -b hotfix  # 旁边开桌处理急事
```

## 十五、新手 FAQ：把最容易绕晕的七个问题一次说清

**Q1：`add` 和 `commit` 到底啥区别？**
逛超市：`add` 是把商品放进购物车，随时能换；`commit` 是推去收银台结账，结完就成了正式存档。

想把放进购物车的某件商品再拿出去、或者同一个文件里只挑几处改动存档？进阶玩法见第四节的「候场区进阶」。

**Q2：`commit` 了但没 `push`，同事能看到吗？**
不能。`commit` 只记在你自己电脑的账本里；`push` 才会寄到云端给大家看。所以攒了几个存档一起 push 是常态。

**Q3：一个分支能同时摊在两个工作区吗？**
不能。一张书桌摊一条线，一条线同一时刻也只能摊在一张书桌上。想在另一个工作区用同名内容？换条分支名开一条就行。

**Q4：`pull` 和 `fetch` 啥区别？**
`fetch` 只把云端的最新情况取下来"看一眼"，不动你的文件；`pull` 是取下来并且当场合并进你当前分支。想先看看再说就用 `fetch`，图省事就用 `pull`。

**Q5：`main` 和 `master` 是啥？两个都有？**
它们是"默认主线"在不同时代的名字：老仓库叫 `master`，2020 年后新建的仓库默认叫 `main`。就是同一样东西的两个称呼，别当成两条线。

**Q6：误删、误 reset，是不是完了？**
九成九能救回来。`git reflog` 记录你 HEAD 去过的每个位置，顺着它几乎总能找到"出事前"的存档点。Git 的设计哲学就是**永远可以后悔**——这也是为什么老程序员敢在代码里大刀阔斧。

**Q7：能直接跳回很早以前的某个版本吗？**
能，而且跳回去不会删掉后面的历史——穿越不等于删除。按你的目的（参观、另开新线、彻底回退……）选命令，见第十二节的「随时跳回任何一个存档点」那张表。

## 收尾：一张总图 + 一句心态

所有概念的关系，一张图收拢：

```
                        GitHub（云端账本，保险柜 + 协作广场）
                          ▲ push（寄上去）      ▼ pull（取下来并合并）
                        ┌─┴─────────────────────────┐
 本地仓库 .git 账本 ────┤  分支 main    ── 主工作区（主书桌）
                        ├  分支 hotfix  ── 附属工作区（加开的书桌）
                        ├  分支 feature ──（躺在账本里，没摊开）
                        ├  历史存档串 ○──○──○──○（每个 ○ 一张快照/存档点）
                        └─  tag v1.0.0 ── 钉在某张存档上的金边名牌
```

最后送你一句老程序员的心得：

> **Git 不可怕，它是这个世界上少有的"允许你无限后悔"的工具。** 放心大胆地开分支、放心大胆地改——只要勤 commit，就没有回不了的头。学习的正确顺序是：先把 `add / commit / branch / merge / push / pull` 这六板斧用熟，其他的（stash、worktree、revert、reflog）都是等你真遇到那个痛了，自然一学就会。

愿你的每一次 commit 都有清楚的说明，每一次 merge 都没有冲突。
